# 0003 - The JIT

Decided for 9.0.0, September 2026, from measurement. sabline-rt
(`decisions/0002-runtime-in-rust.md`) has to answer one question before
its interpreter is written, because the answer changes how the
interpreter is written: does a Sabline runtime need a JIT?

The three choices were **(a)** Cranelift in sabline-rt, **(b)** no JIT
and a fast interpreter, **(c)** keep llvmlite where it is, in the Python
reference runtime. They are not three points on a line: (a) and (b) are
about the Rust runtime and (c) is about the Python one, so the decision
is two halves.

## How it was measured

Everything below is reproducible from this tree. Machine: Windows 11 Pro
10.0.26200, AMD64, 16 CPUs; Python 3.13.13; Sabline 8.6.0; llvmlite
0.49.0; z3 5.1.0. Wall-clock figures, medians after a warm-up, with the
load the machine carried stated where it was taken. MAINTENANCE.md's
rule about quiet machines applies: these are decision-grade, not
CHANGELOG-grade.

1. **Static reach** - which functions the current JIT compiles at all:
   load, check, prove, then `compile_native(funcs, proven)`, per file,
   over `examples/`, `stdlib/` and `benchmark/corpus/`. This is
   `perf_gates.py`'s `JIT_HELPER`, run over a corpus instead of one
   file.
2. **Whole-workload wall time** - `python run_tests.py` and `python
   run_tests.py --no-native`, twice each: 97 examples with expected
   verdicts, including compile, prove, start-up and the programs that
   are refused.
3. **Per-program wall time and run time** - each runnable example run
   with `--time`, native and `--no-native`, median of 3, with
   `--proof-timeout 3 --check-timeout 20` so a slow float refutation
   does not dominate. `[--time] ran in` is the program's own run: not
   start-up, not the check, not the compile. The same for every
   `benchmark/corpus/*.vel`, under the harness's own `--max-memory-mb
   256`, so a program written to exhaust memory is stopped as the
   benchmark stops it rather than by a wall clock. `--timeout` is not
   passed: it moves the run into a child process, which suppresses the
   `--time` line and would measure the wrong thing.
4. **The JIT's own cost** - `python perf_gates.py --only jit --runs 3`.

## What was found

### The JIT reaches very little of the code

| Corpus | Files | Functions | Compiled | Files with any |
|---|---:|---:|---:|---:|
| `examples/` | 104 | 813 | **96** (11.8%) | 35 (33.7%) |
| `stdlib/` | 14 | 173 | **5** (2.9%) | 4 |
| `benchmark/corpus/` | 85 | 160 | **6** (3.8%) | 6 |

And the reach is narrower than 11.8% suggests: most of those 96 are two
functions, `std.is_sorted` and `std.sum_of`, pulled in from `stdlib/std.vel`
by an import and compiled whether or not the program ever calls them.
`native_eligible` refuses anything with an effect, anything fallible,
anything generic, anything returning `Text`, anything recursive, and
anything with an unproven promise - which is most of a program that does
work.

### On the whole suite, the JIT is worth 3%

`run_tests.py`, 97 examples, everything included:

| | median of 2 |
|---|---|
| native | **86.9 s** |
| `--no-native` | **89.8 s** |
| the JIT is worth | 2.9 s, **3.2%** |

### Per program, the JIT loses on 25 of the 30 programs it touches

61 runnable examples, median of 3:

| Group | n | interpreted wall | run time the JIT removes | share of wall | net wall change |
|---|---:|---:|---:|---:|---:|
| all runnable | 61 | 55.67 s | 11.146 s | **20.0%** | **-10.0%** |
| minus `bench.vel` and `native_text.vel` | 59 | 37.21 s | 0.669 s | **1.8%** | **+12.1%** |
| minus every `native_*.vel` and `bench.vel` | 56 | 35.22 s | 0.197 s | **0.6%** | **+12.2%** |

The first row is the number a defender of the JIT would quote. The
second row is what it means: **94% of everything the JIT accelerates in
this corpus is two files written to demonstrate the JIT** -
`examples/bench.vel`, whose header says "burn is compiled to machine
code via LLVM", and `examples/native_text.vel`. Take those two out and
the JIT accelerates 1.8% of wall time and makes the total 12% worse.

Of the 30 runnable examples that compile any function at all, **the JIT
makes 25 of them slower in wall time.** The 31 that compile nothing are
unaffected to within noise (-0.22 s over 17.5 s), which confirms that
llvmlite is imported only when there is something to compile, as
`check_cli.py` requires.

### Why it loses: the cost is fixed and the gain is not

| | |
|---|---|
| importing llvmlite | **79 ms** |
| compiling `examples/bench.vel` (1 function) | **101 ms** |
| observed cost per program that compiles anything | **~177 ms** |

Against that, the run times it is competing with. Here is every runnable
example that compiles something, by run time, interpreted:

| Program | interpreted run | native run | speed-up |
|---|---:|---:|---:|
| `bench.vel` | 15 632 ms | 7 103 ms | 2.20x |
| `native_text.vel` | 1 953 ms | 4.7 ms | 415x |
| `edges.vel` | 340 ms | 197 ms | 1.73x |
| `sandbox.vel` | 271 ms | 247 ms | 1.10x |
| `native_build.vel` | 255 ms | 8.1 ms | 31x |
| `native_list.vel` | 230 ms | 5.9 ms | 39x |
| `ledger.vel` | 18.3 ms | 15.2 ms | 1.20x |
| the other 23 | **3.9 to 7.3 ms** | 3.5 to 6.6 ms | 0.94x to 1.69x |

Twenty-three of thirty programs have a run of under 8 milliseconds. The
JIT spends 177 to win 2. The distribution is what decides this, and it
is not a distribution a better JIT changes: **a Sabline program is a
short program that touches something**, because that is what the
language is for. The programs where machine code pays are the ones
somebody wrote to show that machine code pays.

### The other two workloads agree, for a different reason

**The benchmark corpus** (`benchmark/corpus/`, 85 files, 76 programs in
15 categories), measured the same way, median of 3, each run under the
harness's own 256 MB cap: **the JIT costs 0.33 s and accelerates
nothing measurable.**

| | |
|---|---|
| total wall, native | **28.12 s** |
| total wall, `--no-native` | **27.80 s** |
| the JIT is worth | **-0.33 s**, 1.2% *worse* |
| run time as a share of wall | 2.4% native, 2.2% interpreted |

Of the 85 files, 60 are refused before running, 14 run to the end, and
11 are stopped by a limit - which is the corpus working: these are
programs written to hide a dangerous line, and most of them are supposed
not to finish. Only **6 files compile any function at all**
(`c_skips_last`, `e_pairs`, `a_factorial_25`, `b_square_input`,
`c_sum_of_cubes`, `f_negate_minimum`), and across those six the JIT
saves **3.4 ms of run time** (15.0 ms interpreted against 11.6 ms
native) for **330 ms of wall**. Of the 14 that run to the end, run time
is 0.62 s of 6.0 s of wall, and 0.56 s of that 0.62 s is one program,
`07_infinite_loop/c_slow_but_finite.vel`, which compiles nothing and
which the JIT makes slower rather than faster.

This is the same finding as `examples/`, arrived at from the other
direction: there, the programs that gain are the ones written to
demonstrate the JIT; here, nobody wrote one, and the gain is zero.

**The conformance corpus** (sabline-spec `tests/`, 456 cases): 307 at
L1, 40 at L2, 109 at L3. Only the 40 at L2 run a program - 29 of
`check_sandbox.py`'s escapes, which exist to be refused, and 11 of its
honest programs, which run to the end and print what they must. **416 of
456 cases never reach an interpreter at all**; the L2 programs together
are 11 KB of source and do no arithmetic worth the name. There is
nothing in the conformance corpus for a JIT to accelerate, and there
should not be: it is a corpus about what a budget permits.

## The decision

**(b) for sabline-rt, and (c) for the Python runtime.**

- **sabline-rt gets no JIT.** No Cranelift, no LLVM, no bytecode
  compilation to machine code. A straightforward tree-walking
  interpreter, written for the shape the measurement shows: short runs,
  effect-heavy, dominated by start-up and dispatch. The effort goes into
  the parts the numbers say matter - process start-up, builtin dispatch,
  text handling - and `cargo deny`'s dependency list is where the
  absence is visible.
- **llvmlite stays in the Python runtime, exactly as it is.** `--native`
  and `--no-native` keep meaning what they mean, `fuzz_native.py` keeps
  holding the two engines to agreement on every CI leg, and
  `examples/native_*.vel` keep working. The Python runtime is becoming
  the reference (0002), and a reference's speed is not the thing about it
  that matters.

**The floor that replaces it**, in plan/9.0.md's alpha.8: sabline-rt
interpreting `examples/bench.vel` must be **at least as fast as the
Python runtime with llvmlite**, 7.3 s on this machine, and
`perf_gates.py` fails if it is not. That is a 2.4x interpreter against
the 17.2 s the Python interpreter takes, which is an ordinary result for
a Rust tree-walking interpreter against CPython, and it is written as a
number rather than as a hope. If sabline-rt can beat the Python runtime
*with* its JIT while having none, the JIT was never the thing to build.

### Why not (a), Cranelift

Not because Cranelift is the wrong JIT - it is the right one for this
job, it compiles fast, and its whole design is aimed at exactly the
compile-time-versus-run-time trade-off above. Because of four things the
measurement makes plain.

1. **The gain is 1.8% of wall time** once the demonstration programs are
   removed, and the current JIT already turns that gain into a 12% loss
   by costing more to run than it saves. Cranelift compiles faster than
   LLVM, so it would lose less - it would not win more. The ceiling on
   the win is the 1.8%.
2. **The eligible set is the problem, not the back end.** 96 of 813
   functions compile, and the reasons the other 717 do not - effects,
   fallibility, generics, `Text` results, recursion, unproven promises -
   are language rules, not LLVM limitations. Changing the back end
   changes none of them. Widening the eligible set is a different and
   much larger project, and it would have to preserve
   ARCHITECTURE.md rule 2 - native and interpreted must agree exactly -
   for every case it added.
3. **It is a second code generator to keep honest.** Rule 2 is enforced
   by `fuzz_native.py` on every leg, and `check_mutant_kills.py` has
   killers for the native code's lines. A JIT in sabline-rt would need
   the same apparatus again, in a second language, while the agreement
   gate is already holding two runtimes to each other. That is the
   two-runtime tax doubled, for 1.8%.
4. **It is `unsafe` in the hottest place.** Executing generated code is
   `unsafe` by construction, and plan/9.0.md's rule is that every
   `unsafe` block names an invariant and a test. The confinement layer
   already spends that budget where it has to.

### What would reverse this

Stated as measurements, not as feelings, so that the next person
deciding has a threshold rather than an argument:

- **A real corpus where the accelerable share is above 15% of wall
  time.** Not `examples/`, not `benchmark/corpus/` - programs somebody
  runs. If Sabline is used for something numeric that nobody anticipated
  and the share measured the way section *What was found* measures it is
  above 15% on that corpus, this is reopened. 1.8% and 15% are far
  enough apart that the answer will not be ambiguous.
- **The eligible set passing half the functions in a real corpus.** If
  the language grows so that native code can take effects, fallibility
  or `Text` (each of which is its own design decision, none of them
  planned), the 11.8% figure changes and the arithmetic changes with it.
- **sabline-rt missing its floor by more than 2x after the interpreter
  has had the work alpha.8 budgets for.** If a Rust tree-walking
  interpreter cannot reach the Python runtime's JIT-assisted speed, the
  assumption behind (b) is wrong and that is worth knowing. The response
  is still not automatically a JIT: a bytecode interpreter with inline
  caches is the cheaper next step and comes first.

None of those is true today, and this decision is not provisional. It is
reversible by measurement, which is a different thing.

### One finding that is not a decision

**The JIT makes 25 of the 30 programs it touches slower**, and on the
whole example suite it is worth 3.2% only because `bench.vel` is in it.
A threshold - compile a function only when a loop's trip count or the
program's measured run makes 177 ms worth spending - would make llvmlite
pay on the Python side too. That is not in 9.0's scope, it changes when
a program is compiled and therefore what `--time` reports, and it
deserves its own decision with its own measurement. It is written down
here because it is the most surprising number in this record and the
next person should not have to find it again.
