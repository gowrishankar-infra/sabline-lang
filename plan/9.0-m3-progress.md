## What this checkpoint did

### a. Bounded runs and the Pool through sabline-rt, the limits held by the caller

- **The worker decides, the caller runs.** A pool's worker is confined at
  its start (8.4) and cannot start a process, so with the variable set the
  pool sends its request with `route: true`; the worker checks and proves
  the program under the pool's limits, as it always did, and answers
  `{"route": true}` when sabline-rt may run it - or, when it may not,
  sends `{"routing": why}` (the parent prints the notice) and runs it as
  before (`library._why_not_through_rt`, shared with the unbounded path).
  The pool's process then starts `sabline-rt exec` (`through_rt.run`'s new
  `timeout` and `max_memory_mb`) with what is left of the deadline, while
  it still holds the worker, so `keep_if` is asked of how the run ended:
  the worker is kept only after a clean run, as before. `run(timeout=...)`
  and `run(max_memory_mb=...)` are a pool of one, so they follow.
- **The memory cap.** Windows: the job object a worker gets
  (`library._spawn_capped`), made with sabline-rt suspended. Linux:
  RLIMIT_DATA by `resource.prlimit` before the request is sent -
  `sabline-rt exec` reads nothing of a program before then. Not RLIMIT_AS:
  an idle `sabline-rt exec` maps 72 MB of address space (glibc reserves a
  64 MB arena for its input thread and never touches it) against 2.4 MB of
  VmData, and the run's 128 MiB stack is mapped writable whole, so the cap
  is the program's N plus `through_rt.RESERVED_MB` (the stack, held to
  `PARSE_STACK` by check_through_rt, and 8 MB). Measured in WSL at 16, 32,
  64, 150 and 300 MB: hello runs, the doubling text is E611, deep
  recursion E609, a loop E610 at 2 s. macOS: no prlimit, so not enforced,
  which is what `memory_cap_is_enforced()` already says there. Rust's
  allocation failure says "memory allocation of N bytes failed" and
  aborts: `through_rt.OUT_OF_MEMORY_SIGN`.
- **A run a limit stopped** sends no end frame. Its audit stream is always
  asked for under a limit, and the pool's `_rt_receipt` makes the receipt
  from it (`_RunRecorder.heard`: subjects, refusals, declassifications,
  tool calls, each occurrence counted), `complete: false`, `effects_used`
  null as the package's own is, the producer sabline-rt's from its `start`
  event. A finished run's receipt is sabline-rt's with the pool's
  `timeout`, `max_memory_mb`, start and wall time put in. The stream a
  caller asked for opens with sabline-rt's `start` (naming sabline-rt) with
  the pool's parameters, and ends with the pool's `end`.
- **The command line's `--max-memory-mb`** (undocumented for a run; a
  worker's flag) caps the process with its hard limit left open in rust
  mode, so that sabline-rt can be let past it and held to its own;
  through sabline-rt an E611 prints as the package would.
- `check_pool.py` 39/0 and `check_library.py` 302/1 (the producer-version
  question) through sabline-rt, bounded cases and the door's included;
  `check_hostile.py` 72/0; `check_self_budget.py` 116/0.

## Questions for the maintainer

1. **How should sabline-rt do the network, Python and tools?** Decision 1
   keeps the fallback until it does; this is how it should. Three ways:
   (a) **relay each call to the host**: sabline-rt checks the budget for
   the call - the grant, the count, the refusal, all already ported - and
   records it, then asks the process that started it to make the call over
   the exec protocol (a frame like `read`), and the package makes it with
   the code that makes it today (urllib with its redirects and proxy
   refusal, the granted module, the tool session). Identical behaviour by
   construction, and small; but sabline-rt is then not standalone for
   these effects, and M7's C ABI would need the embedder to supply them -
   natural for Python and a tool, which are the host's by nature, less so
   for the network. (b) **port the network into Rust** - an HTTP client and
   TLS, which means crates where the crate has none (plan/9.0.md's 25-crate
   cap and risk 4), and urllib's messages copied - and relay Python and
   tools as in (a). (c) **leave all three in the package for 9.0**, the
   fallback permanent, and M7's default flip not applying to them.
   Recommended: (a) for all three now, which also gives the gate a way to
   hold them (a stand-in server and a stand-in module), and (b) for the
   network decided at M7, when there is an embedder that is not Python to
   ask for it.

(One choice this checkpoint made that the maintainer may want to overrule,
not blocking: an eval run stays the package's and says so, rather than
being refused under `rust`, because its profile requires confinement.)

## Traps met in this session

- **A suite that scrubs the environment asks nothing of sabline-rt.**
  check_self_budget removes every `SABLINE_` variable before it starts, so
  last checkpoint's "112/0 through sabline-rt" was 112 in the package. Only
  counting who answered each run showed it (0 runs). Any suite that builds
  its children's environment from scratch can do the same; the count is
  the check.
- **check_self_budget's section C finds the variables the package reads by
  pattern**: a string literal or a `*_ENV` constant handed to
  `os.environ`. A variable read through a constant named anything else is
  invisible to it - `through_rt.VARIABLE` was. Name every new one `*_ENV`.
- **RLIMIT_AS is the wrong cap for a Rust process on glibc**: an idle
  `sabline-rt exec` maps 72 MB it never touches (a thread's malloc arena,
  reserved `PROT_NONE`), and a thread's stack is mapped whole. RLIMIT_DATA
  counts what is writable.
- **`datetime.fromtimestamp` refuses on Windows** before 1970 and after
  3001, and `datetime` stops at 9999; `sabline.run` itself refuses an
  instant past 9999 with ValueError, in both runtimes. Epoch plus a
  `timedelta`, and compare a raised error as an outcome.
- **`receipt_statement` is public API**: a keyword added to it moves
  `tests/api/golden.json`. Set what is extra on the statement it returns.
- **A worker under a 16 MB cap cannot start Python**, in either runtime:
  the worker checks the program under the pool's own cap. Test caps a
  Python process can start under.
- **Heredocs halve backslashes - in a Python patch script too** (`"\\n"`
  became a real newline, a `\` continuation joined two lines). Write
  patch scripts with the Write tool, never `cat <<'EOF'`.
- **A `( ... ) &` in the Bash tool outlives the call** with its output
  buffered, so it looks dead and is not; this session rebuilt sabline-rt
  under one. Use `run_in_background`, and list the processes before a
  rebuild.
- The earlier traps stand: a module-level dict in the package fails
  check_pool (this session's `KEPT` was one - pairs now); `Text` is `Rc`,
  so frames are lines; a confined worker cannot start a process; a notice
  on stderr is a difference in every suite comparing it; `cargo fmt`
  writes LF; moving rt code can strand a check_gate injection (checked:
  none stranded).
