## What this shows

Of the 66 dangerous programs, Velaris caught 64 (52 before running, 12 while running) and missed 2. Deno caught 42 (8 before, 34 during) and missed 24. Plain Python caught 31 (all while running, it has no static step) and missed 35. On the 10 control programs the false positives were: Velaris 0, Deno 0, Python 0.

Category 11 runs every tool under the narrowest budget its task needs - Velaris with `fs:read:<dir>`, `net:127.0.0.1:<port>` or plain `io`; Deno with the matching `--allow-read=<dir>`, `--allow-net=<host:port>` or nothing; Python with nothing, since it has no budget. Rows: 11a, 11b, 11c.

Category 12 is indirect authority. In each program the calling code is the same file before and after, and only the declared surface of a dependency it imports changed between two versions of that dependency; the run uses the new version under the budget the task needs. Velaris's static step there is `velaris deps-diff` on the dependency's two versions, which compares their declared surfaces the way `velaris capabilities check` compares a tree with its baseline. It flagged 12a, 12b, 12c before running, and did not flag the control 12d, whose surface narrowed. The compiler alone would not have flagged them: each caller already declared the effect the dependency came to use - net for its own request, fs for the read - so the call type-checks against both versions. Deno and Python have no declared surface per module to compare, so their static steps are the same as in every other category; for a JavaScript or Python dependency, `velaris deps-diff` reports the surface as unknown. Rows: 12a, 12b, 12c, 12d.

What Velaris caught that neither Deno nor Python did: 05a, 05b, 05c, 05d, 05e, 05f. 05a, 05b, 05c, 05d, 05e, 05f: whole numbers are 64-bit and arithmetic that leaves that range stops the program (E407) instead of wrapping or rounding; Python's integers do not overflow and JavaScript rounds to a double, so both print a value without comment.

Flagged by Velaris before running through the termination rule (SPEC.md 9.5), not through an effect: 07a, 07b, 07d, 07e, 07f, 08a, 08b, 08c, 08d, 08e, 08f. `velaris audit` reports `loops_unshown` for a loop whose condition has no counter moving one step toward an unchanging limit, and `check --strict` makes it E612. The rule claims nothing about whether such a loop actually ends; every one of these happens not to, and the run confirmed it.

Caught by Velaris only while running, where a sibling program was caught before: 03c, 03d, 03f, 04e. 03c: a division in main on n - 1, with n from to_int inside a check, is not flagged before running; E403 at runtime. 03d: the same division on the unguarded path is not flagged before running when another path guards it; E403 at runtime. 03f: a remainder inside a loop body is not flagged before running; E403 at runtime. 04e: a read at i + 1 inside a loop bounded by length(xs) is not flagged before running; E602 at runtime. The runtime check (E403 for a zero divisor, E602 for a read out of range) stopped each of them; the prover did not settle the obligation before running. These are the prover's limits as of this version, recorded rather than worked around.

Caught by both, but by Velaris before running and by Deno only once the program reached the call: 01a, 01b, 01c, 01d, 01e, 01f, 02a, 02b, 02c, 02d, 02e, 02f, 06f, 09a, 09b, 09d, 09e, 09f, 11c, 13a, 14a, 14b, 14c. The Deno permission model works at the moment of the call; nothing in `deno check` or `deno lint` reads a file write or a fetch as a problem. Velaris makes the effect part of the function's signature, so `velaris audit` lists it without running anything.

What Velaris missed: 04c, 09c. 04c (c_skips_last): no read is out of range and the function carries no contract, so there is nothing for the prover to refuse; a wrong total is indistinguishable from a right one without a promise about it. 09c (c_command_on_stdout): the only effect is io, which the task needs; the danger is in what a caller does with the text, and no effect system or permission flag sees stdout as dangerous - 10d prints the same words harmlessly, and no tool can tell the two apart.

Python's catches in categories 3 and 6 (03a, 03b, 03c, 03d, 03e, 03f, 06a, 06b, 06c, 06d, 06e, 06f) are crashes on the input this harness supplies (a zero, a non-number, a missing key). With ordinary input those programs run clean, so the catch depends on the test data; Velaris's E520/E705/E706 do not.

Deno's misses in categories 3 to 6 (03a, 03b, 03c, 03d, 03e, 03f, 04a, 04b, 04d, 04e, 04f, 05a, 05b, 05c, 05d, 05e, 05f, 06a, 06b, 06c, 06d, 06e) are JavaScript semantics, not a Deno choice: a division by zero is Infinity or NaN, a read past the end is undefined, a bad parse is NaN or 12, and a large product is a rounded double. All exit 0.

In 02c, 12a, 12b, 12c, 14a, 14b, 14c Deno denied the effect but the program caught the denial (a permission error is an ordinary exception there) and exited 0. The harness credits this as caught-during-run because it watched the socket and saw no request; a caller reading only the exit status would have seen success. A Velaris refusal (E310/E311) cannot be caught by the program.

For Deno and Python the timeout in categories 7 and 8 is the harness's own `subprocess` timeout, not a feature of the tool; Velaris's is the `timeout=` argument of `velaris.run`. The difference is who owns the limit, not whether it fired.

In 08a, 08b, 08c, 08d, 08e, 08f Velaris stopped the program with the timeout (E610), not the memory cap: the interpreter allocates slowly enough that 5 seconds did not reach 256 MB. For Deno and Python the cap and the deadline race, and which fires first varies with the machine's load, so those cells record only that the program was stopped.

Category 5 is a judgement call for Python: its integers do not overflow, so the printed value is arithmetically right and only wrong for a 64-bit consumer downstream. It is recorded as missed because nothing was flagged; a reader who disagrees can discount those 6 rows.
