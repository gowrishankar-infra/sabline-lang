Every release of this major version, newest first, as CHANGELOG.md records it.

9.0.0-alpha.13 - M4: the Windows AppContainer, and sabline eval through sabline-rt #

M4's third checkpoint (plan/9.0.md, M4 - confinement, and a real Windows AppContainer). A run through sabline-rt on Windows happens inside an AppContainer of its own, which is the layer the job object and the lowered token could not be: a process cannot enter one after it has started, so sabline-rt exec reads the request, loads the program to learn which files it reads - a lookahead, never an answer - creates a profile named for the run, grants its SID one ACE per file and per granted directory, starts a child sabline-rt exec --contained SID inside the container with its own standard output and error, pumps the request and the rest of its input through, waits, takes every ACE back and deletes the profile. The child does not take the parent's word for it: --contained is a claim, and the kernel - TokenIsAppContainer, TokenAppContainerSid - is what answers it.

So a Windows run under io is full where a container can hold it, against partial on every release before this one: a read, a write, a connection or a process outside the budget's grants is refused by the kernel, which check_confine.py --runtime rust measures with the fault-injection hook. 90 of its questions pass on Windows 11 and 93 on Linux, none broken. Where a container cannot hold it, it is left off and the receipt says why - a Windows Server, for one, where a process inside a container can open the file it was granted and still not be told what path that file has, so a run would be refused a file its budget allows. That is asked before a run is handed to a container, never assumed. The container is left off, with the reason in the receipt, for a budget granting a loopback host - Windows isolates a container from 127.0.0.1 unless an administrator exempts it - and for one that restricts neither reads nor writes, which a container cannot express without refusing what the budget allows. A run killed before its parent can take the ACEs back leaves them naming a SID nothing can hold again, and the next run sweeps them.

A container is asked before a run is handed to it. A process inside an AppContainer cannot always resolve a path as the process that started it does - on some systems GetFinalPathNameByHandle answers nothing there, and realpath then leaves the path as it was written. Every fs: grant is checked against what a path resolves to, and the host resolves the grant while the run resolves what the program asks for, so such a run would be refused a file its budget allows: a wrong answer, and not a safe one. So the container is asked, once, to resolve the paths the run was granted, and any answer that differs leaves the container off with the reason in the receipt. check_confine.py asks the machine the same question and holds every case to the answer rather than assuming one.

What the container costs, and the two bounds that hold it. An AppContainer reaches a file only through that file's own rights, and Windows' inheritance is a copy and not a lookup, so giving a directory an inheritable ACE writes it into every file under it and taking it back writes them all again - about half a millisecond a file, charged to the run's own deadline. A grant over a tree larger than a thousand files therefore leaves the container off, with the reason in the receipt. And a system whose containers cannot resolve a path remembers that answer for that build of the crate, so it stops making a profile, writing ACEs and starting a probe for a container it will not use; a yes is not remembered, because it would be a claim that outlived its measurement.

fix: the one privilege a confined run keeps on Windows - SeChangeNotifyPrivilege, which is what bypasses traverse checking - was found by LookupPrivilegeValueW alone, and a lookup that failed left the number at zero, which matches no privilege: every privilege was then removed, bypass-traverse among them, and a process that cannot traverse cannot walk to a file it has been given. It is the well-known number (23) unless the lookup answers now. Both runtimes.

ENFORCES, row for row, for both runtimes. sabline-rt os-policy --enforces writes how much of each row of the threat model's table that runtime's kernel holds, one word per system; check_confine.py holds it to be at least the package's everywhere, with a reason on every cell that differs, and all six are Windows'. The table and its exemptions moved out of THREAT_MODEL.md, which was near the size a page of the site may be, into docs/os-enforces.md, as the known-open table did before it.

sabline eval's run is sabline-rt's too. It was the last thing besides sabline trace that stayed in the package under SABLINE_REFERENCE_RUNTIME=rust; the profile's own refusals are still made here, before anything is sent anywhere, and the run goes through sabline-rt like any pool's. sabline-rt honours a stop file - looked for every 256 calls and loop turns, E615 at the next of either, as this package's interpreter has since 8.3 - and a run that has one is started in a process group of its own, so a console break meant for whoever started it does not kill a run that was asked to stop.

A kernel with no Landlock, measured on a runner that has one. There is no honest way to take Landlock off a kernel, and a self-hosted runner is not worth one machine, so the fault-injection hook is asked to take that path: SABLINE_FAULT_NO_LANDLOCK makes the ruleset not be built, the layer report this kernel has no Landlock, and seccomp-bpf be applied as ever. Reads and writes then go through, the network and a process are still refused, and --require-confinement full refuses the run. It is a simulation and the suite and the documentation say so.

The honesty test's hook is behind a feature now. A variable that stands a layer down in a released binary is a variable that turns confinement off, so confine_fault.rs lifts the crate's deny of unsafe with #![cfg_attr(feature = "fault-inject", allow(unsafe_code))] and that feature is not a default: a released crate carries neither its three C calls nor SABLINE_FAULT_NO_LANDLOCK. The suites that measure the confinement build with it. The modules that may lift the deny plainly are four again - confine_appcontainer.rs has joined them - and check_rt.py holds both lists.

This is a pre-release of the sabline-rt crate, and it publishes that and nothing else. 8.8.0 is still what pip install sabline-lang, npm, the Marketplace and the MCP registry give, the Action pins still name 8.8.0's commit, and sabline --version still says 8.8.0. What the Python package on main gained above ships with 9.0.

9.0.0-alpha.12 - M4: sabline-rt confines its own runs, and the command that starts it confines itself #

M4's second checkpoint (plan/9.0.md, M4 - confinement, and a real Windows AppContainer). sabline-rt asks the operating system for the budget's policy in its own process, before the program's first statement: os_policy is ported, confine_linux.rs asks Landlock and seccomp-bpf, confine_macos.rs sandbox_init, confine_windows.rs the job object and the token, and confine_fault.rs is the fault-injection hook that attempts one effect itself. The agreement gate compares the derivation before either runtime asks a kernel for anything - the policy, its digest, what it asks the system to hold and why it asks for nothing, for every budget it has, under --confine strict, without it and under --no-confine - and compares the seccomp filter, the Landlock masks for each ABI and the macOS profile for a fixed set of policies on every platform, not only on the one that applies them. 41,939 comparisons, no differences. check_confine.py --runtime rust asks every question that suite asks of the package of sabline-rt instead: 74 of them, on Windows, with none broken.

The crate has unsafe in it for the first time, in those four modules and nowhere else: every one of those calls is a C entry point the operating system offers, and a crate with no dependencies has no safe wrapper for them. The workspace denies unsafe_code rather than forbidding it - forbid cannot be lifted anywhere - each of the four lifts it with the reason in its own module comment, and check_rt.py holds that list of four, so a fifth is a failing check. Every block carries a // SAFETY: comment naming the invariant and a test that exists, as rt/README.md has required since alpha.1.

What is not done. sabline-rt does not enter a Windows AppContainer yet, so Windows holds neither reads nor the network, exactly as the Python runtime does not - its receipt says so in its own words, which are not the package's, because the reason is not the package's. sabline eval's run is still the package's. M4 is not finished and is not claimed to be.

This is a pre-release of the sabline-rt crate, and it publishes that and nothing else. 8.8.0 is still what pip install sabline-lang, npm, the Marketplace and the MCP registry give, the Action pins still name 8.8.0's commit, and sabline --version still says 8.8.0. What the Python package on main gained above ships with 9.0.

9.0.0-alpha.11 - M3: the network, Python and tools relayed to the package, and the organisation ceiling #

M3's sixth checkpoint (plan/9.0.md, M3 - the interpreter, the budget, Secret and receipts). With SABLINE_REFERENCE_RUNTIME=rust every run now goes through sabline-rt, a run of the network, Python or a tool included: sabline-rt spends the call's effect and relays the call back to the Python package, which makes it with its own code and tells back how it ended and what it recorded (the maintainer's decision of 2026-10-11, in plan/9.0.md). And the organisation ceiling (decisions/0007, item 32c) exists, in both runtimes: a file an operator cannot widen past, held before the budget is given, named in the refusal, the receipt and sabline audit. Every one of M3's exit criteria measures as met; M3 is not declared done, because the fourth criterion's check_pool.py passes only with two of its questions asking each runtime what is true of it - the relay split the ffi cliff - which is the maintainer's to accept (plan/9.0-m3-progress.md). The Python package is the reference, and where the two disagree sabline-rt has a defect.

This is a pre-release of the sabline-rt crate, and it publishes that and nothing else. 8.8.0 is still what pip install sabline-lang, npm, the Marketplace and the MCP registry give, the Action pins still name 8.8.0's commit, and sabline --version still says 8.8.0. What the Python package on main gained below ships with 9.0.

Decided #

The maintainer's answer of 2026-10-11 to the fifth checkpoint's question: sabline-rt does the network, Python and tools by relaying each call back to the Python host over the channel it already uses for output, input and audit events, so that what a call does is identical by construction. Porting the network into Rust is M4's and M5's, and their sections say so. An eval run stays the package's until M4, as chosen last time.

What exists #

The relay. sabline-rt spends the effect of each of the fourteen builtins of the network, Python and tools as it spends every builtin's, and then sends a call frame - the builtin, its arguments, its line - on the sabline-rt exec channel. The host answers with one line: a value (a handle as {"handle", "what"}, which sabline-rt prints and compares as HandleValue does), a failure the program can handle, a coded error, a granted module's exit, or the exception that escaped; and with what its recorder noted while it made the call, in order - each grant's event, each refusal a redirect makes, each tool call - what each grant let through, and the tool session's ceiling. sabline-rt records those in its own receipt and audit stream as they happened, tool_calls and tool_ceiling included. The host's side is runtime.outside_builtin, the package's own code for those fourteen, moved there from run_builtin unchanged, so the package's own runs make the same calls the same way.

Who the host is. For sabline run, sabline test and an unbounded sabline.run, the caller's own process, with the run's budget, seed, clock, arguments and handles installed for the run and put back after (library._hosting) - and the command line's tool session and recorded responses, so sabline run --tools and sabline replay --responses go through sabline-rt too. For a bounded run, a Pool and a PoolRegistry - and so the HTTP door's and the MCP server's runs - the pool's worker that checked the program: confined, capped, the process the package's own run would have made the call in. It answers each call the pool forwards until the run ends, and is killed with sabline-rt at the deadline; one that goes away in a call ends the run as a worker that goes away in a run does.

The fallback's notice is gone, and so is the fallback: what stays the package's is an eval run and sabline trace, each saying so as before. A run whose grants turn the operating system's layer off says so through sabline-rt too, as the command line always has - there is no such layer under sabline-rt before M4, which makes it no less true.

The gate compares those runs. sabline run-dump --through-rt makes the package the host of a run whose three records sabline-rt writes (run_dump::run_hosted), and the gate compares them with the package's own run of the same line, byte for byte: 81 runs - 31 rows written for it, the 24 sandbox rows and 13 sabline-spec L2 cases the gate used to skip, and the ceiling's and the examples' rows that grant more. They run against two stand-in servers on the machine - every reply's date and server fixed - and a stand-in tool host (run_dump.StandInHost). Six new injections in check_gate.py hold the relay's own classes: a failure handed back as a value, an error's line, a handle's text, a grant's event dropped, a grant counted twice, a tool call's secret mark lost.

The organisation ceiling (docs/ceiling.md). sabline.ceiling/1, a JSON object whose allow is a budget, at one system path (the Windows one found through the system's own API, not the environment) and, held as well, the file SABLINE_CEILING names. A budget a ceiling does not wholly cover is E325 before the program is read - naming the file, the first grant past it and what it allows - at every entry point: the command line, sabline test, sabline.run with and without limits, a Pool and a PoolRegistry, the doors, sabline eval and sabline replay. A ceiling that cannot be read refuses every run, saying why. The receipt's run_parameters.ceilings names each one a run was held to - path, sha256, what it allows - refused or not; sabline audit names it and any effect the program needs that it does not grant; sabline ceiling shows what is installed. Several are asked the same question, so no order of asking gives another answer. The rule is Budget.gap, which a door's --max-allow already held requests to; covers now words it. sabline-rt is handed each ceiling's text with its request and reads it, holds the budget to it, words the refusal and names it the same way (ceiling.rs); the gate holds the two to each other over 24 rows, and check_ceiling.py asks every entry point in both runtimes (38 questions), in CI on every leg. Two more injections hold the refusal's words and the receipt's field.

Every program as it is written to run. The gate now runs the twelve examples run_tests.py gives a budget under that budget, and check_through_rt.py runs them through the command line with their own arguments and input; check_benchmark_through_rt.py runs the benchmark's harness in both runtimes - every program under the budget its task needs, with its input, its stand-in server and its vendored library - and compares what Sabline made of each: 102 programs, 84 of them run, 0 differences.

What exists #

A bounded run and the pool, through sabline-rt, the limits held by the caller. A pool's worker is confined at its start (8.4) and cannot start a process, so it does what it always did up to the run - checks and proves the program, under the pool's limits - and says whether sabline-rt may run it; the pool's own process then starts sabline-rt exec under the memory cap and kills it at what is left of the deadline. On Windows the cap is the job object a worker gets, made before sabline-rt runs an instruction; on Linux it is RLIMIT_DATA, set with prlimit before the request is sent - not RLIMIT_AS, because an idle sabline-rt exec maps 72 MB of address space it never touches (glibc's arena for its input thread), and the cap is the program's plus the 128 MiB its run's stack takes. Measured on Linux from a 16 MB cap to 300 MB: a small program runs, the doubling text is E611, deep recursion is E609 and a loop is E610 at its deadline. A run a limit stopped sends no end, so its audit stream is always asked for and the pool makes its receipt from what that says the run did - complete: false, named sabline-rt's. The worker is kept only after a clean run, as before; the sabline-rt process is used once, always.

sabline replay and sabline test through sabline-rt. A replay runs its copy of the program through sabline-rt, held to the replay's own directory and read ceiling; a bounded replay goes through its pool. check_receipts.py's three replays of a run recorded through sabline-rt, which differed in confinement last time, now pass: replayed through sabline-rt too, both say none. sabline test asks sabline-rt to call each test function in turn on one runtime (run_dump::test_relayed) and prints each verdict after what the test printed, as the package's loop does.

The import root in sabline-rt's loader (E515, as loader.py words it, by CPython's realpath), so a run held to an import root - the library's import_root=, a pool's, a replay's - goes through sabline-rt too. The gate holds it: thirteen programs in its tree importing from inside, outside, by .., by a link, from a library, a file that is not .vel, a sibling directory sharing the root's prefix.

What stays the package's, and says so in one line on stderr: a run whose budget grants the network, Python or a tool to a program that uses it (decided); an eval run, whose profile holds a run to the operating system's confinement and does not start one without it; and sabline trace, which shows the package's interpreter at work. A program the checks or the prover refuse runs nothing, and says nothing more.
