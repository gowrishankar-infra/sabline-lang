# 9.0 M4 - where it stands

The record of M4 (`plan/9.0.md`, *M4 - confinement, and a real Windows
AppContainer*) as far as it has got, written so the next session can pick it
up without this one's context. `plan/9.0.md` is the plan; this file records
what was done against it and does not change it. `plan/9.0-m3-progress.md`
is the rung before, which is **done**.

**As of 2026-10-13, third checkpoint (`9.0.0-alpha.13`).** A run through
sabline-rt on Windows happens **inside an AppContainer of its own**, so a
Windows run under `io` is `full` where every release before this one gave
`partial`: a read, a write, a connection or a process outside the budget's
grants is refused by the kernel, measured by the fault-injection hook.
`ENFORCES` is in sabline-rt row for row, as a held/not-held word per system,
and the table moved to `docs/os-enforces.md`. `sabline eval`'s run is
sabline-rt's too, with the stop file honoured there. The doors take the two
confinement flags. The no-Landlock path is measured on an ordinary Linux
runner by simulation. On this machine: `check_confine.py` 134/0 and
`--runtime rust` 90/0 on Windows; 142/0 and 93/0 on WSL's Ubuntu-22.04
(kernel 6.6, Landlock ABI 3); the agreement gate 41,939/0.

### This checkpoint's (`9.0.0-alpha.13`)

- **The Windows AppContainer** (`rt/.../confine_appcontainer.rs`, 1,100
  lines). `sabline-rt exec`, asked for confinement on Windows, is two
  processes. The outer one reads the request, **loads the program to learn
  which files it reads** - a lookahead on a parse-sized stack, never an
  answer, because the child's own load is what refuses anything - creates a
  profile named `sabline.rt.<pid>.<nanos>`, grants its SID **one ACE per
  file and per granted directory** (read and execute for reads; read, write
  and delete for writes), starts a child
  `sabline-rt exec --install-dir DIR --contained SID` inside the container
  with its own standard output and error inherited and a pipe for its
  standard input, writes the request line into it, pumps the rest of its own
  input after it, waits, **takes every ACE back** and deletes the profile.
  It is a byte pump and nothing else, so the frames the run writes go
  straight to whoever asked for the run.
- **The child does not take the parent's word for it.** `--contained SID` is
  a claim; `in_a_container` asks the kernel - `TokenIsAppContainer` and
  `TokenAppContainerSid` - and the claim is made only when the kernel agrees
  *and* the SID is the one named. A sabline-rt started with `--contained`
  outside a container reports `partial` and says its token is not an
  AppContainer's, which `check_confine.py` drives directly.
- **The container is left off**, with the reason in the receipt, for: a
  budget granting a **loopback host** (the maintainer's answer 1 of
  2026-10-12; Windows isolates a container from 127.0.0.1); a budget that
  restricts **neither reads nor writes**, which a container cannot express
  without refusing what the budget allows; a process **already inside** a
  container it did not make; and a profile that could not be made at all.
  Each is a case in `check_confine.py`.
- **A killed run's ACEs** (the maintainer's answer 2 of 2026-10-12). Each
  run writes a record under `%LOCALAPPDATA%\sabline\appcontainer\` - the
  container's SID and one granted path a line - and **holds it open with no
  sharing** while it holds the grants. The next run sweeps every record it
  can open, which is every record no live run holds: it revokes each path
  for that profile's SID and deletes the profile. `check_confine.py` kills a
  run mid-flight, asserts the ACE is left, and asserts the next run takes it
  back.
- **One read-modify-write at a time.** Adding an ACE is *read the rights,
  add to them, write them back*, and two runs doing that to one file at once
  lose one of the two ACEs - the second write is of rights read before the
  first - so a run is refused a file its budget grants. `check_self_budget.py`
  found it (its five programs run on a thread pool). Every grant and every
  revoke now takes a machine-wide lock file first, held for one write and
  not for a run; a run whose turn never comes is not contained and says so;
  a revoke that could not be made leaves the record for the next sweep. Six
  runs at once over one granted directory is a case now.
- **The container is asked whether it can resolve a path, before a run is
  handed to it.** `realpath` answers what file a path names, and every
  `fs:` grant is checked against that; the **host** resolves the budget's
  grants (`Budget.spec()` is resolved) and the **run** resolves what the
  program asks for. Those two agree only while the run can ask the system
  the same question - and a process inside an AppContainer cannot always:
  on the GitHub Windows runner `GetFinalPathNameByHandle` answers nothing
  there, so `realpath` left `C:\Users\RUNNER~1\...` as written while the
  host had resolved the grant to `C:\Users\runneradmin\...`, and the run
  was refused a file its budget allows. That is a wrong answer and not a
  safe one, so `sabline-rt resolve` is run inside the container over the
  paths the run was granted - one process, in the container that is
  already made - and any answer that differs leaves the container off with
  the reason in the receipt. `check_confine.py` asks the machine the same
  question at its start and holds every case to the answer, so a machine
  whose containers cannot resolve is green on the package's own row and
  says so in one line.
- **A latent fault in both runtimes, found on the way**: the one privilege
  a confined run keeps on Windows - `SeChangeNotifyPrivilege`, which is
  what bypasses traverse checking - was found by `LookupPrivilegeValueW`
  alone, and a lookup that failed left the LUID at zero, which matches no
  privilege: **every** privilege was then removed, bypass-traverse among
  them, and a process that cannot traverse cannot walk to a file it has
  been given. It is the well-known number (23) unless the lookup answers
  now, in `sabline/confine.py` and `rt/.../confine_windows.rs`, and
  `the_token_keeps_one_privilege_and_removes_the_rest` holds it.
- **`ENFORCES` row for row, for both runtimes** (*What is next* 2 of the
  last checkpoint, done as the plan asked). `sabline/confine.py` gains
  `ENFORCES_HELD`: for each of `ENFORCES`' rows, one word per system -
  `yes`, `partly`, `no`. `rt/.../confine.rs` gains its own, with a reason on
  each cell that differs, and `sabline-rt os-policy --enforces` writes it.
  `check_confine.py`'s `table_cases` holds the rows and their order to be
  the package's, no cell weaker, every differing cell explained, and the
  page printing each reason word for word. Six cells differ and all six are
  Windows'. The prose stays the package's: a second copy would be two places
  to keep one fact.
- **The page split.** THREAT_MODEL.md was 2,747 bytes from the budget, so
  *What the operating system enforces* - the table, the interpreter's own
  reads, `FFI_WIDENS`, the levels and `EXEMPT` - moved to
  **`docs/os-enforces.md`**, as the known-open table did before it.
  THREAT_MODEL.md keeps the derivation's two paragraphs and a pointer, and
  its *not a security boundary* section says what Windows now holds in each
  runtime. `build_docs.py`'s `DOCS_ORDER` has the new page.
- **`sabline eval` through sabline-rt.** `_EvalPool._kept_by` is gone and
  `KEPT` has one reason left (`sabline trace`). What the profile itself
  refuses is still this package's and is checked before anything is sent
  anywhere. Two things had to move for it:
  - **the stop file**. `Runtime::with_stop_file` looks for it every
    `STOP_EVERY` (256) calls and loop turns and stops with **E615**, in the
    package's words; the request carries `stop_file`, and the pool hands it
    down (`Pool._stop_file()`), because the pool's own process is what
    starts sabline-rt and the worker's `--stop-file` does not reach it.
  - **a process group of its own**. A run with a stop file is started with
    `CREATE_NEW_PROCESS_GROUP` (`start_new_session` elsewhere), so a console
    break meant for whoever started it does not kill a run that was asked to
    stop; the stop file is the only thing that asks.
  `check_eval.py` is 63/0/1 on Windows and 60/0/2 on Linux in **both**
  runtimes, and `check_eval.py` is in `suites_through_rt.py`'s list now.
- **The doors' own command lines.** `sabline serve` and `sabline mcp` take
  `--confine strict` and `--require-confinement full|partial` beside the
  `--no-confine` they had, read by `confine_flags` as every command line
  reads them and carried to every pool the door makes; either beside
  `--no-confine` and the door does not start. `sabline eval` refuses both by
  name, as it refuses `--no-confine`. `confine_flags` is exported from the
  package for the doors, and `check_api.py`'s golden records all three.
- **A kernel with no Landlock** (the maintainer's answer 3 of 2026-10-13: no
  self-hosted runner). `SABLINE_FAULT_NO_LANDLOCK` makes `confine_linux.rs`
  take the `abi == 0` path: no ruleset, the layer reports *this kernel has
  no Landlock*, seccomp-bpf as ever. `check_confine.py`'s
  `no_landlock_cases` then holds that reads and writes go through, the
  network and a process are still refused, `--require-confinement full` is
  E326, and the same run without the variable is `full` - so the leg
  measures a difference. It runs in `confine_rt`'s ubuntu leg, and the
  suite, `docs/confinement.md` and that job's comment all say it is a
  simulation.
- **The honesty test's hook behind a feature** (the maintainer's answer 2 of
  2026-10-13). A variable that stands a layer down in a released binary is a
  variable that turns confinement off, which `check_self_budget.py` exists
  to refuse, so `confine_fault.rs` lifts the deny with
  `#![cfg_attr(feature = "fault-inject", allow(unsafe_code))]` and the
  feature is not a default. Behind it: the three C calls (a Unix socket,
  `kill(pid, 0)`, a bind mount) and `SABLINE_FAULT_NO_LANDLOCK`. The
  attempts that need no C call - a read, a write, a connection, a process -
  are in every build, because each is something whoever set the variable
  could do themselves. `check_rt.py` holds the shape: `MAY_BE_UNSAFE` is
  four again (`confine_appcontainer.rs` has joined, `confine_fault.rs` has
  left), `BEHIND_A_FEATURE` is the fifth, the module must lift it that way
  and not plainly, the feature must be declared and must not be a default.
  Every CI job that runs a suite builds `--features fault-inject`;
  `publish-crate.yml` and `release.yml` do not.
- **A Windows bug the suites found.** `sabline.run(source)` through
  sabline-rt wrote the source to a temporary file in **text mode**, so the
  receipt's subject digest was of bytes with a carriage return before every
  line feed rather than of the text passed in. `_source_to_file` writes with
  `newline=""` now. It also closes `check_library.py`'s producer-version
  question, which was `BY_DESIGN` in `suites_through_rt.py` "until M4": the
  producer a receipt names is now compared against the runtime that
  answered.
- **The documents**: `docs/os-enforces.md` (new), `docs/confinement.md`'s
  *The Windows AppContainer* section, THREAT_MODEL.md, `rt/README.md`'s
  unsafe section, MAINTENANCE.md, the CHANGELOG's three new top-level lines
  and the alpha.13 entry, `plan/9.0.md`'s M4 section and pre-release table,
  and this file.

## Questions for the maintainer

1. **Should `sabline audit`, `sabline doctor` and `confine.predict()` answer
   for the runtime that will run the program?** They answer for the Python
   package's own today, whatever `SABLINE_REFERENCE_RUNTIME` says. On
   Windows that is now the weaker of the two, so a prediction never promises
   more than the run gets - but `--require-confinement full`, which the
   audit says would be refused on Windows, succeeds through sabline-rt. The
   alternatives are (a) as it is, and the audit document stays the same
   bytes wherever it is made; (b) `predict()` takes the runtime, which means
   the package modelling sabline-rt's Windows behaviour - the second copy of
   one fact that `ENFORCES_HELD` was shaped to avoid; (c) the audit prints
   both columns, as `docs/os-enforces.md` does. Recommended: (a) until M7
   flips the default runtime, then the prediction is that runtime's.
2. **Should a budget granting `net` with no host also leave the container
   off?** Your answer of 2026-10-12 leaves it off for a budget granting a
   loopback *host*, because no AppContainer may reach 127.0.0.1. A plain
   `net` grant allows every host, the loopback address among them, and this
   checkpoint keeps the container on for it: the budget does not say it
   needs the loopback address, and while the network is relayed to the
   process that started sabline-rt nothing is lost. When the network is
   ported into Rust (item 1 above) a `net` run that tries `localhost` would
   be refused by Windows with nothing from Sabline explaining it. The
   alternatives are (a) as it is, and decide it with the port; (b) leave the
   container off for `net` with no host too, which costs every such run its
   file confinement on Windows; (c) keep the container and have the run's
   own failure name the container when a loopback connection is refused.
   Recommended: (a) now, (c) with the port.
3. **Should the resolution probe's answer be remembered?** It is the same
   answer every time, because it is a property of the operating system and
   not of the run, and on a machine where it says *no* every run pays for
   a profile, a set of ACEs and a probe process it will not use - which is
   the Windows Server case, so it is not hypothetical. It could be written
   beside the lock file and read instead: free after the first run on a
   machine, and stale after an operating-system upgrade. The alternatives
   are (a) as it is, measured per run; (b) remembered in that file, with
   the Windows build number in it so an upgrade asks again; (c) remembered
   only for the process, which helps a pool and nothing else, since each
   `sabline-rt exec` is its own process. Recommended: (b), next session,
   with the build number as the key - but measure the cost first, because
   `perf_gates.py` does not measure a run through sabline-rt at all and
   that is the gap that let this one in.
4. **Is a fault worth having for "the container could not be made"?** The
   fallback - the job object, the token, the reason in the receipt - is what
   a Windows machine that refuses `CreateAppContainerProfile` gets, and
   nothing tests it, because every runner can make one. The hook already has
   a way to stand Landlock down; the same shape would stand the container
   down. Recommended: yes, one more fault behind the same feature, next
   session; it is an hour and it is the one Windows path with no test.

## Traps met in this session

- **A run inside a container may not see the file system the way its
  parent does.** It could read the file it was granted and still resolve
  the path to that file differently, which no escape test would catch -
  the suite that caught it was `legitimate_cases`, the one that asks
  whether *nothing legitimate breaks*. Two lessons: a confinement rung
  needs the "nothing breaks" half of the suite as much as the honesty
  half; and **a claim about a kernel measured on one Windows is a claim
  about that Windows** - the spike ran on Windows 11 Pro and CI runs on
  Windows Server, and they differ.
- **A read-modify-write of an object's rights is not atomic**, and two runs
  at once are two runs reading before either writes. The symptom was not a
  crash: it was a run refused a file its budget grants, in a *different*
  suite (`check_self_budget.py`, whose five programs run on a thread pool),
  thirteen cases failing with "read failed" where the baseline read it. The
  lesson is the usual one twice over: **run the suite that shares state
  between runs, not only the one that tests the feature**, and when a
  Windows ACL is edited from more than one process, hold a lock across the
  whole read-modify-write.
- **`cargo test` and `cargo build` without `--features fault-inject`
  silently replace the binary the suites use.** Nothing says so; the honesty
  test simply reports that the attempt was not made. Build with the feature
  after any plain `cargo` command.
- **A path that an AppContainer cannot reach does not exist to it.**
  `Path::exists()` answers false on access denied, so `sabline eval`'s stop
  file - which is outside every grant on purpose - was never seen and the
  run ran to its time limit instead of stopping. The container has to be
  given the stop file's directory, and `Extras::stop_file` is how.
- **The bash heredoc here halves a backslash.** `"...\\n"` written inside a
  `python - <<'PY'` script arrives as a real newline, which turned a Rust
  string in `through_rt.py` into a syntax error. It is the same trap as the
  patch script's line continuation, one layer further down: **write a file
  with the Write tool, or an edit with the Edit tool, when the text holds a
  backslash.** And `git checkout <file>` to undo the damage undoes every
  other change to that file too - make the edit, not the revert.
- **rustfmt moves an `unsafe` away from its `// SAFETY:` comment** when the
  line it is on grows; `check_rt.py` then says the comment is missing. Put
  the comment inside a block whose only content is the call
  (`let x = { // SAFETY: ... \n unsafe { ... } };`). This caught one call
  again this session, so it is not a one-off.
- **A new page under `docs/` cannot be dated until it is committed**:
  `build_docs.py` reads the sitemap's dates from what HEAD holds, so the
  first `check_site.py` after adding one fails on a stale sitemap however
  many times the docs are rebuilt. Commit, rebuild, commit the sitemap.
- The earlier traps stand: a notice on stderr is a difference in every suite
  that compares it; one folder for both runtimes, remade for each; read a
  failure's message before believing the claim it is about; a Windows build
  will not relink while a stray `sabline-rt.exe` runs.
