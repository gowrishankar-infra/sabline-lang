The binary has two new commands: `sabline-rt check --install-dir DIR
[--list PATHS | FILE]` and `sabline-rt tables`. rt/README.md states the
check document's format; `src/checker.rs`'s header says which of the
reference's behaviours are copied on purpose and why.

**In the Python package**: `sabline/check_dump.py` writes the same
document (`sabline check-dump`, unlisted, beside `ast`), and the builtin
tables (`sabline check-dump --tables`). It runs `load_program`,
`check_main` twice (as a check and as a run asks), `check_effects` and -
only when those found nothing - `check_types`, exactly as `sabline check`
does, without `check_proofs`, and `loop_termination` for every function.
`raised` records which stage ended the check by raising, because the
command and `sabline.check` read a raise differently, and the suites are
held to the second.

**In the gate**: `check_agreement.py` makes three comparisons - the AST
dump (M1), the check document, and the builtin tables - and
`agreement_checks.py` is the checkers' corpus. `check_gate.py` has four
new injections, one per new comparison class, each of which turns the
gate red.

**In the suites**: `suite_runtime.py` is what `--runtime rust` means.
Under it a suite asks sabline-rt every check-time question, holds the
answer to what it holds the Python package's to, and counts each question
it did not ask by why: a run (M3), the prover's (Python's for good,
decisions/0002), an audit (a Python command), the check ceiling, an
import root, another command. A question not asked is never counted as
passed.

## What the port copies on purpose

Each of these looks like something to tidy, and tidying it would make the
two runtimes disagree:

- **`infer` runs again where the reference runs it again** - three times
  on a map's first value, twice on a key quoted in a message. Inferring a
  function value checks that function and appends what it finds, so the
  number of calls is visible in the problem list. It also makes nested
  maps exponential in both runtimes, deliberately the same.
- **A lifted function value's name runs across every file one load
  parses** (`Parser.lambda_n` is a class attribute in Python). The check
  document sets it to zero per program, as the AST dump does.
- **`qualify` renames a library's lifted function and not the `Closure`
  that names it**, because the reference's walk skips every field called
  `name`. That is what reaches E402 at `checker.py` 460.
- **Paths are joined the way CPython joins them**, not normalised:
  `D:\x\examples\lib/util.vel` is a correct answer on Windows.
- **CPython's `str.strip()` strips U+001C to U+001F**, which Rust's does
  not, and `expr_str` writes a float with CPython's `repr` (`1e-05`,
  `1e+16`).

## Questions for the maintainer

These are decisions, and they are not made here.

**1. The input-bounded loop verdict, as decisions/0006 (c) words it, is
not sound - and it names the wrong file.** The rule: "a loop whose every
path from the top of its body back to the condition calls `read_line()`,
and whose condition changes only from that call's result, ends when its
input ends". `read_line()` answers `""` at the end of input, every time
it is called after that (`sabline/runtime.py`). So this loop fits the rule
and never ends once its input does:

    fn main() uses io {
        let going = true
        while going {
            let line = read_line()
            if line == "x" {
                going = false
            }
        }
    }

18a ends only because its exit is keyed to the empty text (`if line ==
""`). A rule that is sound and still syntactic, proposed for the decision
rather than decided: every path through the body calls `read_line()`; and
the loop leaves when that call answers `""` - either the condition is a
test that the value read is not empty (`line != ""`, `length(line) > 0`)
with that value assigned only from `read_line()`, or the condition is a
flag that is assigned only `false`, and only in the arm of an `if` that
tests that the value read on that path is empty. Then each turn consumes
a line and the first turn after the input ends leaves, so the loop runs
at most one more time than there are lines. linkcheck.vel's `gather` and
18a both meet it; the loop above and 18e do not; Euclid (18b) does not
either, and must not.

Separately, 0006 and `plan/9.0.md` say the verdict is written into
"sabline-spec §9.5" first. sabline-spec's §9.5 is *When one grant covers
another*. The two loop verdicts are defined in this repository's own
`SPEC.md` §9.5, and sabline-spec only refers to that rule, from the
audit's `loops_unshown` field. The likely meaning is: this `SPEC.md`
§9.5 gains the third verdict, and sabline-spec's `loops_unshown`
description says an input-bounded loop is not counted - but that is for
the maintainer to say.

Nothing of the verdict is built. Once decided it is about two days, in
the order 0006 gives: the spec text first, then `sabline/termination.py`
and `termination.rs` in the same commit, with 18a reported bounded and
passing `check --strict` in both, 18e and the one-arm loop staying
`unshown`, 05a-05f and 18f still E407, and `check_termination.py` gaining
the cases. The check document's `loops` already carries `verdict` and
`why`, so the gate compares the third verdict with no change to it.

**2. L3's 51 `check` cases are `sabline capabilities check`, which 0002
keeps in Python.** `sabline/conform.py`'s `_conf_check` builds a tree,
writes a baseline from `capability_scan` (an audit of every program in
it), applies the change and runs `capabilities_compare`. decisions/0002
lists `capabilities` and `audit` among the commands not ported, and the
plan's own M2 text says L1's `audit` cases "belong to commands that stay
in Python". As written, the criterion asks sabline-rt to answer a
question 0002 says it never will. Either the criterion meant something
else, or the capability scan's per-program half (what each program may
touch) is meant to come from sabline-rt - which would be a change to
0002, and would need the audit's derivation of paths and hosts ported.

**3. `sabline conformance --runtime rust` "drives sabline-rt through the
C ABI"** - and the C ABI is M7's. M2 could do it through the `sabline-rt`
binary, as the agreement gate and the suites do now, and move to the C
ABI when M7 builds it; or M2 could build the first entry points of the C
ABI early. The first is cheaper and changes nothing M7 decides; it is
still a departure from the plan's words.

## What is not done, in the order to do it

1. **Port the budget parser** (`sabline/budget.py`'s grammar: effects,
   scoped `fs:`/`net:`/`ffi:`/`tool:` grants, counts, the path resolution
   R of sabline-spec §5.1, the refusals), and hold it to L1's 280 `budget`
   cases. It needs no decision: M3 needs it to run anything, and the plan
   puts it in M2 because a run must parse its budget. It is the largest
   piece left. Whether the cases are driven through the binary or the C
   ABI is question 3.
2. **The input-bounded verdict**, once question 1 is answered.
3. **L3's `check` cases**, once question 2 is answered.
4. **A checker target for the differential fuzzer**: `fuzz_parsers.py
   --target agreement` feeds generated input to both parsers; a target
   that feeds generated well-formed programs to both checkers would find
   what the fixed mutations do not. Not an exit criterion; recommended.
5. **A two-file case** for `checker.py` 460 (a library with a function
   value, imported under a name), which needs the gate to carry a
   directory rather than a file. Small, and the last reachable gap.

## A pre-release

None was cut, and `rt/Cargo.toml` still says `9.0.0-alpha.4`. A
pre-release is a shippable tag with the agreement gate green, and several
may be spent inside one milestone, so this checkpoint could have been one.
It was not, for one reason: question 1 is open, and its answer changes
what the termination stage reports, so a crate published now would
publish a checker whose loop verdicts M2 has already decided to change.
crates.io keeps every version for good. The next checkpoint that settles
question 1 and ports the budget parser is the natural `9.0.0-alpha.5 -
M2: ...`, made the way RELEASING.md says: the version in `rt/Cargo.toml`,
the CHANGELOG heading naming M2, a row in `plan/9.0.md`'s table, and the
workflow tagging it.
