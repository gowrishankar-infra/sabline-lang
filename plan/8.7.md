# 8.7: Evidence

**A plan. Nothing here is built, and this file builds nothing.** No
code changes with it, no version moves with it, and no number in it is
a measurement. Every figure below is a target or a shape, and the only
honest sentence this file can carry today is that the work has not been
done.

## Why

`paper/sabline.md` §5 now says, for each piece of related work, where
that work is **ahead** of Sabline. Three of the entries are ahead in the
same way:

- **CaMeL** reports results on AgentDojo.
- **TypeGuard** (language-based agent control) reports AgentDojo's Slack
  suite: 21 user tasks, 5 injection tasks, 105 attack pairs, all 105
  resisted with policies on, 15 of 21 benign tasks completed without
  them and 8 with them.
- **ChainCaps** reports 82 tasks on five frontier models, attack success
  from 25-68% down to 0-4.8%, benign completion 96-100%.

Sabline reports none. §4.1's benchmark counts defects a tool catches -
66 defective programs and 10 correct ones, written three times each -
which is a real measurement of a real thing, and it is not a
measurement of what happens when somebody is trying to get past the
tool. §6 says so, and now says it as a limitation of its own.

Abdelnabi, Hicks, Rieck and Sadeghi
([arXiv:2605.22568](https://arxiv.org/abs/2605.22568), cs.CR) name three
weaknesses that make such measurements untrustworthy: **vulnerabilities
in the benchmark itself**, **temporal staleness**, and **runtime
uncertainty**. Their paper is the reason this one is a plan with
countermeasures rather than a list of numbers to go and get. Each piece
below says which of the three it is exposed to and what it does about
it.

## The constraint: nothing here costs money

Every item runs on GitHub's free runners, or on a machine the
maintainer already has, or not at all. That rules some things out, and
they are named in **What is not here** at the end rather than left to
be discovered. Where a model API is needed, the run is offline and
replayed from recorded responses, as `agent_loop.py --metric --offline`
already works today; a run with a key is the maintainer's own and is
never a required check.

## 1. AgentDojo, comparable to CaMeL, TypeGuard and ChainCaps

**What it is.** Sabline evaluated on AgentDojo, reported so that a
reader can put its numbers beside the three above without doing
arithmetic.

**The shape.** AgentDojo gives an agent a set of tools and a user task,
and injects an attacker's instruction into the data the tools return.
Sabline's place in that picture is the runner's tool door (8.5): the
agent writes a Sabline program, the program calls tools through `tool`,
and the operator's budget bounds which tools, which arguments and how
many calls. So the harness is:

1. An AgentDojo tool suite is expressed as a Sabline tool manifest
   (`sabline.tools/1`) - the tools, their schemas, their ceilings.
2. Each user task becomes a request to a model, answered with a Sabline
   program, run under a budget written for that suite.
3. The injection is delivered exactly as AgentDojo delivers it, in what
   a tool returns.
4. Two numbers per suite, AgentDojo's own: **utility** (benign tasks
   completed) and **security** (injections resisted).

**Report both budgets.** Every number is given twice: under a budget
written for the task, and under `--allow all`. The second is the
control, and it is the number that says how much of the result is
Sabline's language and how much is the operator's budget. A paper that
reported only the first would be reporting the operator.

**What must be said about it, whatever it shows.**

- Sabline has no information flow and no per-value budget. The
  laundering cases AgentDojo contains - read something, summarise it,
  send it - are inside a budget that grants the read and the send, and
  Sabline will fail them. `decisions/0004` and its Amendment 1 are the
  design that would not; neither has shipped. **The expected result is
  that Sabline scores worse than CaMeL and TypeGuard on security and
  the reason is structural**, and the report leads with that rather
  than burying it.
- What Sabline should do well on is the part AgentDojo does not mostly
  test: an injected instruction that asks for an operation the budget
  does not grant at all - a new host, a path outside the grant, a tool
  that is not in the manifest, a call past the ceiling. Those are
  refused before the operation, and the receipt names the refusal.
- A result that is better than expected is a reason to look for a
  defect in the harness before it is a reason to publish.

**Against the three weaknesses.** *Benchmark vulnerabilities*: the
harness is published with the results, and the suite version and
commit are pinned and named in every table. *Temporal staleness*:
AgentDojo is a public benchmark and models are trained after it, so
each result names the model, its version and its date, and the offline
replay's recorded responses are committed so the same run can be made
again. *Runtime uncertainty*: every task is run three times and the
report gives all three, not a mean; a task whose three runs disagree is
listed as disagreeing rather than averaged away.

**What it takes.** The manifest translation and the runner harness are
the work; the rest is `agent_loop.py`'s shape applied to somebody
else's tasks.

## 2. Model round trip, per model, against Python

**What it is.** `agent_loop.py --metric` already measures one thing:
given a task, how many attempts does a model need before it produces a
Sabline program that compiles, holds its budget and passes its test.
Ten tasks, recorded replies, no network. This item makes it a
comparison rather than a number.

**The shape.**

- The same ten tasks in **Python**, scored by the same rule - does it
  run, does it do what the task said - so the metric is "how much
  harder is Sabline than Python for this model", not "how good is this
  model".
- Per model, not pooled. A single number over several models hides the
  thing worth knowing, which is whether the gap narrows for newer ones.
- The three parts of a failed attempt reported separately: it did not
  compile (and the error code), it compiled and was refused by the
  budget (and the code), it ran and did the wrong thing. Those are
  three different problems and only the first is the language's syntax.
- Recorded and replayable, as today. A run with a key is the
  maintainer's and produces the recording; the required check replays
  it.

**Why it belongs in an evidence plan.** It is the one number that
speaks to the premise of the whole project - that a model can write
this language - and today it exists for one model and has no baseline.
A claim about a language models can write, with no comparison to the
language they actually write, is not evidence.

**Against the three weaknesses.** *Temporal staleness* is the acute one
here: model versions move monthly. Every figure carries the model's
exact version string and the date, results are never carried forward to
a newer version, and a table row whose recording is older than six
months is marked stale by the harness rather than by a reader noticing.

## 3. Competitor scoring on the Sabline benchmark

**What it is.** §4.1's benchmark - 76 programs, 66 with one defect and
10 correct, in 15 categories - is run against tools other than Deno and
Python, and **every loss is published**.

**The field.** Five, each chosen because it makes a claim that overlaps
Sabline's:

| | Why it is in the field | What it should win |
|---|---|---|
| **Deno** permissions | already in the paper; scoped grants in a language people use | subprocess cases, which Sabline does not model |
| **WASI** (a component under Wasmtime) | handle-based authority, enforced at a VM boundary | anything where the boundary matters more than the declaration |
| **Starlark** | deterministic, no I/O at all, used for exactly this | every category that is about reaching something, by having nothing to reach |
| **a Python sandbox** | the thing most people actually reach for | little, and the point is to measure how little, fairly |
| **a CaMeL-style setup** | provenance and permitted readers per value | every laundering category, which is where Sabline has no answer |

**The rule that makes it worth reading: losses are published.** For
each category, the table says which tools caught the defect and which
did not, and Sabline's misses are in the same table as everybody
else's, with the same prominence. A benchmark written by the project it
flatters is worth nothing unless its failures are as easy to find as
its successes. The paper's §6 already names Sabline's two misses;
this extends that rule to every competitor's win.

**Against the three weaknesses.** *Benchmark vulnerabilities* is the
acute one, and it is the most serious risk in this whole file: the
benchmark was written by this project, and a benchmark written by a
project is a benchmark shaped by what that project does. Three
countermeasures, and none of them is sufficient:

1. **Every category states, in advance, which tools it expects to
   catch it and why.** A category that only Sabline is expected to
   catch is either a real property or a rigged question, and writing
   the expectation down first is what makes the difference visible.
2. **A category no competitor catches is suspect**, and is reviewed
   before it is published, not after.
3. **The corpus is published with the results** and the invitation to
   add a category is in `CONTRIBUTING.md`. A category contributed by
   somebody who wants Sabline to lose is worth more than three written
   here.

## 4. The CTF, on free runners, with a hall of fame

**What it is.** A standing invitation to get past a Sabline budget, run
on infrastructure that already exists, with the people who succeed
named.

**The shape.**

- A set of programs and budgets, published, each with one claim: this
  program under this budget cannot do X. `check_sandbox.py`'s 39
  escapes and `check_adversarial.py`'s recorded passes are where the
  first ones come from; they are already written and already hold.
- A submission is a program, a budget and a transcript. It runs on a
  GitHub free runner in a workflow of its own, in the same confinement
  a release runs in, and reports one of three answers: the claim holds,
  the claim is broken, or the submission did not run.
- **A broken claim becomes a case in `check_adversarial.py` in the same
  week**, which is the rule every previous adversarial pass has
  followed, and is the only thing that makes the exercise worth
  anything. A CTF whose findings are not turned into tests is a
  publicity stunt.
- `HALL_OF_FAME.md` already exists and already has the shape: the
  finder's name as they want it written, what they found, and the
  commit that closed it.

**What it is not.** It is not a bug bounty; `SECURITY.md` says there is
no money, and this does not change that. It is not evidence that
Sabline is secure - a CTF that nobody attacks proves nothing, and
§6 will go on saying the budget is not a security boundary whatever the
CTF shows. It is a way of finding the next defect earlier than the
adversarial passes have found the last four.

**Against the three weaknesses.** *Runtime uncertainty*: a submission
that only sometimes works is the most interesting kind, and the harness
runs each one five times and reports the count rather than a verdict.
*Benchmark vulnerabilities*: the claims are the benchmark here, and
each one is a sentence somebody can argue with, which is the point.

---

## What is not here, and why

- **Anything that costs money.** No paid evaluation service, no model
  credits as a required check, no hosted infrastructure, no paid
  runners, no bounty. Every item above runs on free runners or on the
  maintainer's own machine. This is a constraint and is stated as one,
  not as a preference: a plan whose numbers depend on a budget that
  does not exist is a plan that will not be executed.
- **A user study.** §6 says there has not been one and this does not
  change that. It needs people, and the honest version needs more of
  them than this project can ask.
- **A formal claim about any of it.** None of these four produces a
  theorem. The theorem work is `plan/9.0.md`'s *After the candidate*:
  budget non-escape and `Secret` non-interference in Lean 4. Numbers
  and proofs answer different questions and neither substitutes for the
  other.

## The order

1. **Model round trip** (2), because the harness exists and the
   baseline is a day's work, and because it is the number that most
   changes what the rest of the project should do.
2. **Competitor scoring** (3), because the corpus exists and the losses
   are the part that has to be published before anybody will believe
   the wins.
3. **AgentDojo** (1), because it is the largest, and because the result
   it is most likely to produce - Sabline losing on laundering - is one
   `decisions/0004` already predicts, so running it before M6 measures
   the thing 0004 is for.
4. **The CTF** (4), last, because it needs an audience and the first
   three are how one is earned.

Nothing above has a date, because nothing above has been started.
