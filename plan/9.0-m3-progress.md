# 9.0 M3 - where it stands

The record of M3 (`plan/9.0.md`, *M3 - the interpreter, the budget,
`Secret` and receipts*) as far as it has got, written so that the next
session can pick it up without this one's context. `plan/9.0.md` is the
plan; this file records what was done against it and does not change it.
`plan/9.0-m2-progress.md` is the record of the rung before.

**As of 2026-10-11, sixth checkpoint.** With `SABLINE_REFERENCE_RUNTIME`
set to `rust`, **every run goes through sabline-rt**, a run of the
network, Python or a tool included: sabline-rt spends the call's effect and
relays the call back to the Python package, which makes it with its own
code (the maintainer's decision of 2026-10-11). Only an eval run and
`sabline trace` stay the package's, saying so. **The organisation ceiling**
(decisions/0007, 32c) exists in both runtimes. The gate compares the
relayed runs and the ceiling's, and every program now runs as it is
written to run somewhere in the comparison: the examples and the
benchmark under their own budgets too. It is pre-release
**`9.0.0-alpha.11 - M3: the network, Python and tools relayed to the
package, and the organisation ceiling`**: `rt/Cargo.toml` says that
version, and release.yml tags it and publishes the crate when the merge
commit's tests pass. Nobody tags by hand.

**Every one of M3's exit criteria measures as met, and M3 is not declared
done**: the fourth criterion's `check_pool.py` passes through sabline-rt
only because two of its questions now ask each runtime what is true of it,
and the relay made that true differently - the `ffi` cliff is split
(*Questions for the maintainer*, 1). That is the maintainer's to accept or
not. The table below says each criterion and its number.

## The maintainer's decision of 2026-10-11, and what was done

The fifth checkpoint left one question - how sabline-rt should do the
network, Python and tools. The answer, now in `plan/9.0.md`'s M3 section:

1. **sabline-rt relays each call back to the Python host**, over the
   channel it already uses for output, input and audit events, so that
   behaviour is identical by construction. Done (a, below).
2. **Porting the network into Rust is M4's and M5's**, and those sections
   say so now. Nothing of it was started.
3. **An eval run stays the package's until M4**, as the fifth checkpoint
   chose. Unchanged.

Then, in the order asked: the relay (d) and the organisation ceiling (e).

## What this checkpoint did

### a. The relay: the network, Python and tools

- **sabline-rt** (`interp::RELAYED`, the fourteen builtins of the network,
  Python and tools): the effect is spent as for every builtin, then a
  `call` frame - name, arguments, line - goes on the exec channel and one
  line comes back, `{"answer": ...}`: `value` (a handle as `{"handle",
  "what"}`; `Value::Handle` prints as `HandleValue` does and compares by
  identity), `fail`, `error`, `exit` (a granted module's SystemExit) or
  `raised`; and `did` (the host recorder's notes in order: each grant's
  event, each refusal a redirect makes, each tool call), `counted` (what
  each grant let through - a tool's grant is counted without an event, as
  the package does), `tool_ceiling` (the session's record after a tool
  call). sabline-rt records them in its own receipt and stream, so the
  receipt is sabline-rt's and says what the package's would: `tool_calls`
  and `tool_ceiling` included (`receipt::Kind::Tool`). A run nobody hosts -
  the gate's own batch - answers `NotPorted`, as before.
- **The package** (`runtime.outside_builtin`): the fourteen bodies moved
  out of `run_builtin` verbatim, which calls it after the spend; the host
  (`through_rt.answer`) calls it without the spend, under a recorder that
  keeps what the call notes (`_HostRecorder`).
- **Who the host is.** The command line, `sabline test` and an unbounded
  `sabline.run`: the caller's own process, with the run's budget, seed,
  clock, arguments and handles installed for the run (`library._hosting`,
  as `_run_program` does) and put back after - and the command line's tool
  session and recorded responses, so `--tools`, `--record-responses` and
  `replay --responses` go through too. A bounded run, a Pool, a
  PoolRegistry (and so the doors): the pool's worker that checked the
  program - confined, capped - which after answering `{"route": true}`
  serves each forwarded call (`pool._host_relays`) until the parent says
  `{"relayed": true}`. The deadline kills sabline-rt and the worker; a
  worker that goes away in a call (`through_rt.HostGone`) ends the run as
  a worker gone in a run does (`_no_answer`).
- **The fallback is gone** (`not_ported`, `fallback_notice`, `NOT_PORTED`
  deleted). `KEPT` holds `checks`, `ceiling`, `source`, `eval`, `trace`.
  The command line's warning that a grant turns the operating system's
  layer off is printed through sabline-rt too (true: there is no such
  layer before M4), so stderr stays the same.
- **The gate**: `sabline run-dump --through-rt` (`run_dump.run_hosted`,
  `exec` request `dump: true`, `run_dump::run_hosted` in the crate):
  sabline-rt runs the line as the gate's batch does - STDIN, ARGS, the step
  and size limits, output kept in the document - relays only the calls,
  and its end frame carries the three records as canonical text, written
  verbatim. `check_agreement.py` runs every budgeted row that is not
  `_ported` that way and compares it with the package's run of the line:
  `agreement_runs.RELAYED_RUNS` (31 rows: fetch, post, request,
  fetch_status, redirects followed and refused, a refused scheme, nothing
  listening, TLS against plain HTTP, E314, E315, E317 by a proxy and a
  granted proxy, the py family, handles, py_json, E311 two ways, an exit
  from Python, `all`, tools answered, E320 to E323 every way, a secret),
  the 24 sandbox rows and 13 sabline-spec L2 cases that had been skipped,
  6 ceiling rows and 7 examples. Two stand-in servers (`agreement_runs.
  servers()`, each reply's date and server fixed) and a stand-in tool host
  (`run_dump.StandInHost`). Six injections in `check_gate.py` for the
  relay's classes.
- **check_through_rt.py**: the relayed rows (but those needing a tool
  session) through the command line, `sabline.run` with and without limits
  and a PoolRegistry - 88 runs - and the two relayed lists held equal
  (`relayed_lists_agree`: the crate's `RELAYED`, the package's
  `OUTSIDE_BUILTINS`, and every builtin of net, ffi and tool).
- Unit tests: `tests/unit/test_runtime.py` (the host's answers; a held_to
  of two grants; Python through every route; the clock stopping a call the
  worker is making; a worker gone in a call); `tests/exec.rs` (a relayed
  call answered as a host would).

### b. The organisation ceiling (decisions/0007, 32c)

- **The file**: `sabline.ceiling/1`, `{"schema", "allow", "description"}`,
  `allow` a budget. One system path - `/etc/sabline/ceiling.json`,
  `/Library/Application Support/Sabline/ceiling.json`, `Sabline\ceiling.json`
  under Windows' ProgramData found by `SHGetKnownFolderPath`, not the
  environment - and, held as well, the file `SABLINE_CEILING` names
  (`sabline/ceiling.py`; `CEILING_ENV`, varied by check_self_budget's C17).
- **The rule**: before a run is given its budget, every ceiling must cover
  all of it (`Budget.gap`, which `covers` - the doors' `--max-allow` - now
  words; the Rust port beside it in `budget.rs`). Otherwise **E325**, line
  0, before the program is read, naming the file, the first grant past it
  and what it allows. A ceiling that cannot be read refuses every run.
  Several are asked the same question, so order cannot change the verdict.
- **Where it is held**: `library._run_program` (so `sabline.run`, every
  pool's worker, the doors, eval, replay), the command line's `_cli_run`,
  `sabline test`; the routes to sabline-rt refuse first (`KEPT`
  `ceiling`), so the package reports it, receipt and all.
- **Where it is named**: the refusal; the receipt's
  `run_parameters.ceilings` (`[{"path", "sha256", "allow"}]`, always
  present); `sabline audit` (*THIS MACHINE'S CEILING*); `sabline ceiling
  [--json]`. docs/ceiling.md; docs/receipts.md.
- **In sabline-rt** (`src/ceiling.rs`): the exec request and a line of the
  gate's list carry each ceiling's text (`{"path", "text"}`); sabline-rt
  reads it, holds the budget to it and words E325 the same, and names it
  in its receipt. The gate's `agreement_runs.CEILING_RUNS`, 24 rows; two
  injections.
- **check_ceiling.py** (CI's test job, every leg): 38 questions - the
  command line, `sabline test`, `sabline.run` with and without limits, a
  Pool, a PoolRegistry, eval and replay, in both runtimes; the receipt; a
  broken ceiling; `sabline ceiling`, `--json`, `sabline audit`; two
  ceilings in either order; the system path unmoved by the environment.

## Questions for the maintainer

1. **The `ffi` cliff is split through sabline-rt; is that accepted?** A
   granted module's code runs in the host, so it reaches the host's state:
   what the host checks of a call - the network's hosts and ports, the
   module grants, the tool grants - and not what sabline-rt holds - the
   effects, the file grants, the counts. In the package everything is one
   process, so a program granted unscoped `ffi` can add `fs` to
   `sabline.state.EFFECT_BUDGET` and read a file (`check_pool.py`'s "the
   cliff is real"); through sabline-rt the read is E310. So the relay is
   narrower, never wider. `check_pool.py` now asks each runtime what is
   true of it - the package's cliff, sabline-rt's refusal - and holds both
   to the reset that matters with a cliff both share (a net host a program
   granted itself is not there for the next program on the same worker).
   (a) **Accept it as is** for 9.0, and say it in THREAT_MODEL.md when M4
   rewrites the confinement rows. (b) **Hold the host's grant checks in
   sabline-rt too** - the host and port of a URL, the module a call names,
   the tool grants - so a granted module can widen nothing sabline-rt runs
   but `ffi_reach`, which needs Python's objects; that is the port M4 and
   M5 already make of the network and the tool door. (c) **Treat the
   difference as a failure** until (b), which would leave M3's fourth
   criterion unmet until M5. Recommended: (a), with (b) arriving with M4
   and M5 as planned - and M3 then declared done at this checkpoint.
2. **Should the package's native engine word E407 and E602 as its
   interpreter does?** Its own rule is "only allowed to be faster, never
   different", and today a run's error message depends on whether llvmlite
   is installed; under `rust` it is always the interpreter's. (a) Fix the
   native engine: record the operator and the line where it overflows and
   reads, and have `fuzz_native.py` compare the coded lines of stderr; (b)
   leave it until the default flips at M7, which makes every run's message
   the interpreter's. Recommended: (a), as its own small item outside the
   ladder.
3. **The spec**: should the next sabline-spec version define the ceiling
   file (`sabline.ceiling/1`), E325 and `run_parameters.ceilings`, with a
   conformance case or two? Recommended: yes, in the next spec release.

## Traps met in this session

- **A suite that runs a command without giving it an input hangs when the
  suite itself has an open standard input**: `sabline eval` reads its
  program's input, and the background shell's pipe never ends. Give every
  subprocess `input=""` or `stdin=DEVNULL`.
- **The benchmark's harness runs the package natively** (`sabline.run`'s
  default), and the gate compares the interpreter: hold sabline-rt to the
  package with `--no-native`, or the native engine's own wording reads as
  sabline-rt's difference.
- **A relative `fs:` grant resolves where the caller is**: a library run in
  a suite resolves `fs:read:data` against the suite's directory, not the
  program's.
- **One folder for both runtimes, remade for each** - again: a path is in a
  receipt's subjects and its budget, so per-runtime folders make every row
  differ (the examples' first run here, eleven "differences").
- **`--freeze-time` on the command line takes an ISO 8601 instant**, not
  epoch seconds (the run document's lines take seconds).
- **A pool rebuilds a receipt's `run_parameters` from its own limits**:
  anything a worker put there beyond them (the ceilings) has to be carried
  over by name.
- **Heredocs halve backslashes** - four more times this session, in patch
  scripts and in a test's Sabline source. Write patch scripts with the
  Write tool; edit a file holding `\\` with the Edit tool.
- The earlier traps stand: a module-level dict in the package fails
  check_pool; `Text` is `Rc`, so frames are lines; a confined worker cannot
  start a process; a notice on stderr is a difference in every suite that
  compares it; `cargo fmt` writes LF; moving rt code can strand a
  check_gate injection; don't rebuild sabline-rt while a job spawns it.
