# 9.0: the Rust runtime

The plan. `decisions/0002-runtime-in-rust.md` says what sabline-rt is
and what "9.0 done" means; `0003-jit.md` decides the JIT from
measurement; `0004-untrusted.md` designs `Untrusted of T`;
`0005-breaking-set.md` lists every other break. This file is the ladder,
the gate that holds it, the criteria for retiring the Python runtime,
and the risks.

Nothing here starts work. No runtime code changes on this branch.

## The ladder

Each alpha is a shippable tag - `9.0.0-alpha.N` on PyPI and crates.io -
with the agreement gate green. An alpha that cannot ship is not done,
and the next one does not start.

Effort is **days of work**, not calendar days, by one person who knows
this compiler and is learning Rust. MAINTENANCE.md and SUPPORT.md say
what else that person is doing. Multiply by whatever you believe about
a single maintainer's throughput; the ratios between the alphas are the
part worth trusting.

### alpha.1 - lexer, parser, and the same AST

sabline-rt reads a Sabline program and builds the same tree the Python
parser builds, over the whole corpus. The parser is the stage where two
implementations most easily differ in ways nothing notices until much
later, so it is first and it is checked by equality, not by sampling.

**The canonical dump.** Both runtimes write the AST as one canonical
JSON document: every node kind, every field, in a fixed key order, with
`for` already desugared to `while` and inline functions already lifted
(ARCHITECTURE.md: the parser does both, so nothing later has to know
about them). Integer literals as decimal text, floats by the shortest
round-tripping representation, text as JSON strings. `sabline ast
--json` writes it from Python; `sabline-rt ast` from Rust. The dump is
not a stable format and is not in `tests/api/golden.json`: it is a
comparison surface, and STABILITY.md's "anything else in the package"
clause covers it.

**Exit criteria**

- Byte-identical dumps for all 104 `examples/*.vel`, 14 `stdlib/*.vel`,
  85 `benchmark/corpus/*.vel`, every program in the conformance corpus
  and in `check_sandbox.py`'s 39 escapes and 19 honest programs.
- Every program that Python refuses at lex or parse time, sabline-rt
  refuses with the same code (E000, E002, E100, E101, E102) and the same
  line and column.
- `fuzz_parsers.py` grows a mode that feeds each generated input to both
  and requires the same outcome: the same tree, or the same code.
  Coverage-guided, as it is today.
- Blocks nested more than 4,000 deep are E102 in both, as 8.2 made them
  in Python (STABILITY.md's 8.2 row) - the one place a Rust parser's
  natural recursion would differ, and it differs by crashing.
- `sabline-rt` publishes to crates.io from Actions by OIDC (crates.io
  Trusted Publishing), with no token stored, as PyPI, npm and the MCP
  registry already do (MAINTENANCE.md's secrets table gains no row).
- The agreement gate exists, runs on every commit, and covers the parser.

**CI legs added**: `rust` (build, `cargo clippy -D warnings`, `cargo
test`, `cargo deny check`, `cargo vet`) on ubuntu-latest,
ubuntu-24.04-arm, windows-latest, macos-latest and macos-15-intel; an
MSRV leg pinned to the stated minimum Rust version; `agreement`.

**Effort**: 18 days.

**The risk that would slip it**: the dump turning out to be a second
specification. If the Python parser's tree has shapes it never meant to
promise - a field that is sometimes absent, a lifted function's
generated name depending on a dictionary order - then making the dumps
equal means changing Python, and every change to Python is a change to
the reference. Mitigation: the first three days go to dumping the Python
tree and reading it for exactly this, before any Rust is written.

### alpha.2 - types and effects

The effect checker and the type checker, including `Secret of T`, the
Secret sink rules (E560), the generic-binding rule, E562 and E563, and
the rules for `main`. Termination comes with them, since `check
--strict`'s E612 is a verdict.

**Exit criteria**

- For every program in the four corpora: the same verdict (compiles, or
  refused), the same set of error codes, the same order, the same lines,
  and the same **message text**. Messages are not covered by
  STABILITY.md - "Codes are stable; prose is not" - but two runtimes
  whose messages differ will drift into two behaviours, and
  `tests/error_messages` already holds every message to a golden. Both
  runtimes are held to that one golden.
- `check_refusals.py`, `check_secret.py`, `check_termination.py`,
  `check_error_messages.py` and `check_fallible.py` run against both and
  pass against both.
- The conformance corpus at L1 and L3 passes against sabline-rt
  (`sabline-rt conformance`), and `build_conformance.py --check` still
  agrees with the suite tables that generate it (ARCHITECTURE.md rule 8).
- Inferred types agree: the gate compares `sabline check --json`'s
  problems and `proven` set, with `proven` empty on both, since neither
  proves yet.

**CI legs added**: none. The `agreement` job grows to compare verdicts,
codes and messages; `check_error_messages.py` gains a `--runtime` flag.

**Effort**: 22 days.

**The risk that would slip it**: `check_types.check_fn.infer` is the
second most complex function in this compiler (214, MAINTENANCE.md) and
its behaviour is defined by itself. Where it does something the SPEC does
not state, the Rust checker has to copy the behaviour, and finding those
places is the work. Mitigation: `check_mutants.py` already names the
lines in `checker` that no suite reaches; those are the first places to
look, and the mutants that survive are a list of undocumented behaviour.

### alpha.3 - the interpreter, the budget, and receipts

The run itself: `run_builtin` for all 77 builtins, the budget's every
grant and refusal, the guarded opener, counts, the read ceiling, the
time and memory limits, `Secret` tracking at runtime (which is nothing -
a Secret has no runtime representation), the recorder and
`sabline.receipt/1`.

**Exit criteria**

- For every runnable program in the four corpora: the same exit status,
  the same stdout bytes, the same coded errors on stderr, the same
  refusals in the same order.
- The same receipt, field for field, after normalising exactly the list
  in *The agreement gate* below and nothing else.
- `check_sandbox.py`'s 39 escapes are refused by sabline-rt with the
  same code at the same place; its 19 honest programs run.
- `check_library.py`'s 56 budgets and 27 audits, `check_fallible.py`,
  `check_money.py`, `check_hostile.py`, `check_self_budget.py`,
  `check_pool.py` and `check_receipts.py` pass against sabline-rt.
- Money is exact and in one currency, and floats are IEEE-754 with the
  same printing: `check_money.py` and `examples/floats.vel` byte-agree.
  Rust's default float formatting is not Python's, and this is where
  that is found rather than at rc.
- Whole-number arithmetic stops with E407 outside 64 bits in both,
  unary minus of the smallest whole number included (8.2's row).
- `fuzz_agreement.py`: generated programs run in both, coverage-guided,
  the way `fuzz_native.py` holds the native and interpreted engines
  today.
- The lie corpus: every false promise is left to a runtime check in both
  and breaks at run time with the same code (sabline-rt does not prove,
  so every promise is a runtime check there; that the *runtime* check
  fires identically is what is being shown).

**CI legs added**: `fuzz_agreement` on every leg, 30 seconds, as
`fuzz_parsers.py` runs today; the monthly run gets 20 minutes of it.

**Effort**: 35 days. The largest single step, and `run_builtin` is 181
complexity across 77 builtins.

**The risk that would slip it**: text. Sabline's `Text` is Python's
`str` - UTF-32 code points, `length` counting them, `code_at` giving
one - and Rust's `String` is UTF-8 bytes. Every text builtin (`length`,
`code_at`, `slice`, `split`, `chars`, `upper`, `lower`, `contains`,
`format`) has to count what Python counts, and a lone surrogate, an
astral character or an unpaired combining mark is where it will not.
Mitigation: the text builtins are written first, against a generated
corpus of exactly those inputs, before anything else in the interpreter.

### alpha.4 - confinement, and a real Windows AppContainer

`sabline/confine.py`'s whole policy in Rust: `os_policy` (one
derivation, budget to policy), Landlock, seccomp-bpf, the macOS profile
through `sandbox_init`, the Windows job object and lowered token - **and
the AppContainer that Python could not enter.**

**Exit criteria**

- `check_confine.py` passes against sabline-rt on every platform, with
  the fault-injection hook (`SABLINE_FAULT_INJECT`) ported: the runtime
  itself attempts an effect outside the budget and the kernel refuses it
  (E319), or lets it through exactly where `ENFORCES` says it is not
  held, and always lets it through under `--no-confine`. This is the
  honesty test, and it is the one that must not be weakened to pass.
- `ENFORCES` in sabline-rt holds **at least** what
  `sabline/confine.py`'s holds, row for row, on every platform, and
  strictly more on Windows: **reads held to the `fs:read:` grants**, and
  **the network refused with no `net` grant**, which today say "not
  held: it needs an AppContainer, which this Python cannot start in".
- THREAT_MODEL.md's Windows row is rewritten to what is then true, and
  `check_docs.py` holds it to the table, as it does today.
- A receipt's `confinement` says `full` on Windows for a budget where it
  says `partial` today, and `os_policy_sha256` is over the same
  canonical policy document in both runtimes for the rows both hold.
- `sabline eval` runs under sabline-rt and refuses every relaxation of
  its profile (`check_eval.py`).

**CI legs added**: `confine-rt` on Linux (Landlock ABI 4+ and a leg on a
kernel without Landlock), Windows and macOS; the AppContainer assertions
run on windows-latest.

**Effort**: 18 days, **after** the spike below succeeds. If the spike
fails, this alpha ships without the AppContainer, the Windows row of
THREAT_MODEL.md is unchanged, and the release note says so plainly
rather than quietly.

**The risk that would slip it**: the spike. See the risk register.

### alpha.5 - the runner's tool door

`sabline/tools.py` in Rust: `read_manifest` (`sabline.tools/1`), the
JSON Schema subset, `held_by`, the ceilings, `ToolSession` on standard
input and output, and E320 to E324.

**Exit criteria**

- `check_runner.py` passes against sabline-rt: fourteen ways past
  `to=*@corp.com`, five ceilings, a host that lies eleven ways.
- The door's bytes agree: for a recorded host transcript, both runtimes
  write the same `ready`, `call` and `exit` lines, in the same order,
  with the same JSON key order.
- `sabline replay` of a receipt recorded under one runtime runs under
  the other and reports no difference (`check_receipts.py`), which is
  the strongest single statement the two can make about a tool run.
- The argument-pattern rule is implemented from sabline-spec section
  5.6 and not from the Python code, and the corpus is what says they
  agree. A pattern matcher written by reading another pattern matcher
  inherits its defects.

**CI legs added**: `runner-rt`.

**Effort**: 8 days. The smallest alpha: the door is one protocol, and
`check_runner.py` is already adversarial.

**The risk that would slip it**: `_cli_run_with_tools` opens the session
before the program is read, "because a confined process may not be let
start the door's reader thread" (ARCHITECTURE.md). The ordering between
the door's reader, the confinement call and the first statement is
load-bearing and is not written down anywhere but that sentence.
Mitigation: write it down, as a numbered sequence, before porting.

### alpha.6 - `Untrusted of T` and the breaking set

0004 and 0005, in **both** runtimes, in the same commits. This is the
one alpha where Python changes as much as Rust, and it is late on
purpose: the gate has to be trustworthy before it is used to keep two
implementations of a new language feature in step.

**Exit criteria**

- `Untrusted of T` in both: the sources, the sinks, `trust`, the tenth
  effect, E570, E571, E572, the `untrusted` object of the audit and
  `trustings` in the receipt, the SARIF rule and
  `--allow-trust-reasons`.
- The breaking set in both: `fs:delete`; the `db` effect with
  `db:read`/`db:write` and E312; `db.vel` parameterized, with `run` and
  `rows_json` gone; `sabline add` holding to `[index]` with a recorded
  `--outside-index --reason`; the nine deprecations removed; `sabline
  receipt show --as runtime-trace`; the `review` ceiling; the budget
  parser refusing a write grant to where the host imports from.
- `sabline migrate --to 9.0` does everything 0004 and 0005 say it does,
  including refusing to insert a `trust` or to turn an interpolation
  into a parameter list, and `check_docs.py` holds each claim.
- The conformance corpus gains the cases sabline-spec section 12.11
  names, `build_conformance.py` writes them, and the drift test passes.
- sabline-spec's section 12 stops being a draft, in the version that
  tracks 9.0.0.
- `check_rename.py` is rewritten to assert each deprecation is gone
  rather than present.
- The 8.5 case in `docs/runner.md` - a tool result that steers a path
  inside the budget - is a case of `check_runner.py` that now fails to
  compile, in both runtimes, and `docs/runner.md`'s "What is not here
  yet" section is deleted rather than edited.

**CI legs added**: none. Every existing suite runs against both.

**Effort**: 22 days.

**The risk that would slip it**: the standard library. `http.vel`,
`rest.vel` and the four batteries change signatures, and
`check_batteries.py` holds each of `azure.vel`, `github.vel`, `k8s.vel`
and `aws.vel` to a stand-in for its service, "a Signature Version 4
checked the way AWS checks one". A signature computed over a value that
is now `Untrusted` has to keep computing the same bytes. Mitigation: do
the standard library first in this alpha, not last.

### alpha.7 - embeddings

The C ABI, and five bindings over it.

**Exit criteria**

- `tests/api/golden.json` is **unchanged**. `sabline.run` and
  `sabline.Pool.run` call sabline-rt through `ctypes`; their signatures,
  their parameters and every field of `RunResult` are what the golden
  records. `check_api.py` passes with no `--update`, and the release
  gate would refuse a release whose golden differed without an `api:`
  line - so the absence of that line is the proof.
- `SABLINE_REFERENCE_RUNTIME` does what MAINTENANCE.md reserved it for:
  unset or `rust` runs sabline-rt, `python` runs the package, and the
  conformance, differential and benchmark jobs read it. It selects which
  runtime *runs*; it does not and cannot disable the agreement gate (see
  the gate's own test).
- Node over N-API, Go over cgo, Java over JNA, Rust as a crate: each
  runs `examples/discount.vel`, refuses a program that fetches a URL,
  and returns the same receipt as Python, in a smoke test on every leg.
- The C ABI is fuzzed: null pointers, non-UTF-8 bytes, a handle used
  after it is freed, two threads on one handle. Every one is a coded
  error or a refusal, never a crash and never undefined behaviour.
- `EMBEDDING.md`'s "The embedding limit" section is rewritten. Today it
  says there is no in-process embedding for Node, Go or Rust "and there
  will not be one until the compiler is something other than a Python
  package". That sentence is what this alpha exists to delete.
- `sabline eject` and the playground still work: eject writes a
  directory that runs with nothing from here, and the playground still
  puts a Sabline in a browser. Neither can carry a `cdylib`, so both
  keep the Python runtime, and `check_eject.py` says so.

**CI legs added**: `embed-node`, `embed-go`, `embed-java` on Linux,
Windows and macOS; `abi-fuzz` on Linux.

**Effort**: 20 days.

**The risk that would slip it**: the pool. `sabline.Pool` resets every
mutable global between programs (ARCHITECTURE.md rule 6), and
`check_pool.py` scans the package for module-level state that is in
neither list. A Rust library has its own state, invisible to that scan,
and a pool that leaks between programs is worse than a slow one - rule
6 says exactly that. Mitigation: the C ABI gives each run its own
opaque handle with no process-global state at all, and `check_pool.py`
gains a scan of the Rust crate for `static mut`, `lazy_static`,
`OnceLock` and `thread_local`.

### alpha.8 - the JIT decision, implemented

`decisions/0003-jit.md` decides (b): **no JIT in sabline-rt, a fast
interpreter**, and llvmlite stays in the Python reference runtime where
it is. This alpha is what that costs to make true and to keep true.

**Exit criteria**

- sabline-rt has no JIT, no Cranelift dependency, and `cargo deny`'s
  dependency list says so.
- A performance floor in `perf_gates.py`: sabline-rt's interpreted
  `examples/bench.vel` is **at least as fast as the Python runtime with
  llvmlite** - 7.3 s on the machine 0003 measured - and the gate fails
  if it is not. 0003's numbers say the interpreted Python runtime takes
  17.2 s on the same program, so the floor is a 2.4x interpreter, which
  is an ordinary thing for a Rust tree-walking interpreter and is stated
  as a number rather than a hope.
- The whole-workload numbers of 0003 are regenerated against sabline-rt
  and published in the release entry, in the same form, so the next
  person deciding this has a second data point.
- `perf_gates.py --only numeric --against` compares sabline-rt with
  sabline-rt, and the 25% rule holds as it does today.
- If the floor cannot be met, this alpha does **not** ship a JIT to
  cover it. It ships the number, and 0003 is reopened with the
  measurement that reverses it, which 0003 states in advance.

**CI legs added**: the release `perf` job gains the sabline-rt floor.

**Effort**: 4 days if the floor is met by an interpreter written
straightforwardly; 15 more if it is not and the interpreter needs
work (a bytecode form, inline caches for the builtin dispatch). The
second number is the one to plan for.

**The risk that would slip it**: measuring on a busy machine and
believing it. `perf_gates.py` already reports how busy the machine was
and refuses fewer than three runs for a gate; the floor is taken on a
quiet machine, as MAINTENANCE.md says every number that goes in a
CHANGELOG is.

## The agreement gate

Designed here, built in alpha.1, grown by every alpha after it.

`check_agreement.py`. It runs both runtimes over the same inputs and
fails on any difference. It is the single thing that makes two
implementations cheaper than one implementation plus hope.

### What it runs over

| Corpus | Size | What it exercises |
|---|---|---|
| sabline-spec's conformance corpus | 456 cases: 307 at L1, 40 at L2, 109 at L3 | budgets, audits, runs, derivation, covering, bounds |
| `examples/` | 104 `.vel` files, 97 with an expected verdict in `run_tests.py` | the language, verdict by verdict |
| `benchmark/corpus/` | 85 `.vel` files: 76 benchmark programs in 15 categories, and the libraries two categories vendor | programs written to hide a defect from a tool |
| the lie corpus | `check_prover_lies.py`'s false promises | a promise that must break at run time, in both |
| `check_sandbox.py` | 39 escapes, 19 honest | Goal C, case by case |

### What it compares

1. **The verdict**: compiled, refused, ran, and the exit status.
2. **The output**: stdout byte for byte; stderr's coded lines, which are
   the ones that carry a code and a line.
3. **The error code and the message**, and the line and column.
4. **The receipt**, field for field.
5. **The audit** document, field for field, where one is produced.

### What is normalised, and nothing else is

Four things differ by construction. Each is listed here, and **a field
joining this list needs its own argument in the pull request that adds
it**, because each entry is a place the gate stops looking.

- `producer.name` and `producer.version` - one says `sabline-lang`, the
  other `sabline-rt`. They are supposed to differ.
- `startedAt` and `wall_time_ms` - a clock and a duration.
- `subject[*].name` where it is `<source>` for a program given as text -
  identical in practice, listed because it is derived from a path.
- The confinement fields (`confinement`, `confinement_reason`,
  `confinement_layers`, `os_policy_sha256`) are compared by **rule, not
  by equality**: sabline-rt's level must be at least Python's on the
  same budget and platform, and never less. alpha.4 makes it strictly
  greater on Windows, so equality would fail there for the right reason.
  The gate prints every row where they differ, and the release entry
  lists them.

Nothing else. Not the order of a list, not the spelling of a message,
not a float's printed form.

### That it cannot be turned off

Three things, and the third is the one that matters.

1. **It reads nothing that could disable it.** `check_agreement.py`
   takes the corpus paths and nothing else: no environment variable, no
   config file, no flag that skips a corpus or a comparison. A test
   scans its source for `os.environ`, `getenv` and any `argv` beyond
   those paths and fails on a match - the way `check_pool.py` already
   scans the package for module-level state and `check_workflows.py`
   reads the scheduled workflows.
2. **The workflow cannot skip it.** `check_workflows.py` gains a rule:
   the `agreement` job exists in test.yml, has no `if:` and no
   `continue-on-error`, runs on push and on pull_request, and is in the
   release gate's required set. A pull request that removes it fails on
   itself.
3. **It is proven to detect, not merely to run.** The gate's own test
   builds sabline-rt with one deliberate difference injected - a
   single error code changed, a single message changed, one receipt
   field dropped - and asserts the gate goes **red** for each. A gate
   that has never been shown to fail is a gate nobody has tested. Three
   injections, one per comparison class, run on every commit on Linux.
   This is `check_mutant_kills.py`'s idea applied to the gate itself.

Every environment variable Sabline reads is set to a plausible
disabling value (`SABLINE_REFERENCE_RUNTIME=python`, `CI=`,
`SKIP_AGREEMENT=1`, `SABLINE_NO_AGREEMENT=1`) in a fourth case, which
asserts the number of compared cases is unchanged.

### Where it runs

Every push to main and every pull request, as a job of test.yml, on
Linux, Windows and macOS. The nightly runs it against installed
artefacts rather than a checkout. The release gate requires it green.

## Demotion criteria for the Python runtime

9.0 does not retire the Python runtime; it makes the Rust one the one
that runs. Retiring it is a separate decision with a separate bar, and
this is the bar. All four, not any of them.

1. **Green agreement runs.** 60 consecutive green agreement runs on
   main, **and** two minor releases after 9.0.0 shipped with it green,
   **and** at least 90 days since 9.0.0. Sixty is chosen against this
   project's own rate: main has 222 commits in its life and a minor
   release has taken between 2 and 22, so sixty commits is roughly three
   minors' worth of change with no difference found. A number larger
   than the project's whole history would be a number nobody intends to
   reach.
2. **Every escape target refused at least as early.** For each of
   `check_sandbox.py`'s 39 escapes and the conformance corpus's 40 L2
   run cases: where Python refuses at compile time, sabline-rt refuses
   at compile time; where Python refuses at an operation, sabline-rt
   refuses at that operation or before. Never later, never not at all,
   and the comparison is recorded case by case rather than in aggregate.
3. **An outside attack pass against sabline-rt.** The standing
   adversarial prompt (`.github/adversarial/PROMPT.md`), aimed at
   sabline-rt, for eight consecutive weekly runs with every finding
   reproduced and either fixed or dismissed in writing; **and** one
   review by a person who is not the maintainer. The second is the one
   that may not be affordable - SUPPORT.md says there is one maintainer
   - and if it cannot be had, that is written down as an unmet criterion
   and the demotion does not happen. Three models agreeing is not an
   outside review; they read the same way.
4. **A date, which is the earliest and not a deadline.** **2027-06-01.**
   Before it, nothing is removed whatever the other three say. On or
   after it, and only with the other three met, the standalone
   executables, the Docker image and the npm wrapper carry sabline-rt
   alone, and the Python runtime becomes **reference only**: still on
   PyPI, still installed by `pip install sabline-lang`, still the
   definition of what a program means, still able to run every program
   sabline-rt runs, and no longer inside the artefacts a user gets when
   they did not choose Python. If the criteria are not met, the date
   moves. A date that forces a removal is a date that will be met by
   lowering the bar.

Whatever else changes, the Python runtime is never removed from the
repository while it is the reference, and
`SABLINE_REFERENCE_RUNTIME=python` keeps selecting it.

## The risk register

### 1. The two-runtime tax

**What it is.** Every language change is written twice, and the second
writing is in a language the maintainer is learning. The tax is not the
first port; it is the next four years of every new builtin, every error
code and every confinement rule costing twice.

**What is done about it.** The scope decision in 0002 is the main
answer: one command is ported, not thirty. The agreement gate is the
second: a change that is made in one runtime and not the other fails on
the commit that makes it, not six months later. And the demotion
criteria are the third - the tax is meant to end.

**What would make it unpayable.** A year in which the gate is green but
nothing else ships. The signal to watch is the ROADMAP's "Now" list
standing still for two releases in a row; if it does, 9.0 is consuming
the project rather than serving it, and the honest response is to stop
at the alpha that is done and ship it as a minor with sabline-rt
optional.

### 2. Bus factor one

**What it is.** SUPPORT.md says it already: "A single maintainer. Real,
and stated." Two runtimes with one maintainer is one maintainer with
twice the surface, and the Rust half has no second reader.

**What is done about it.** Nothing that removes the risk, and this
register does not pretend otherwise. What is done: the C ABI is small
and documented, so a second person could bind it without reading the
interpreter; the agreement gate means a newcomer's change is checked by
a machine against a reference implementation rather than by review
alone; `decisions/` exists so that why is written down and not only
what; and demotion criterion 3 requires an outside reader at least once.

**What would make it worse.** Removing the Python runtime early. It is
the second implementation *and* the fallback, and while there is one
maintainer it is worth more than the tax it costs.

### 3. Windows AppContainer, for a Rust binary - **spike this first**

**What it is.** The whole Windows half of alpha.4 rests on a claim
nobody has tested: that a statically linked Rust binary can start inside
an AppContainer and still do its job, where `python.exe` cannot.
`sabline/confine.py` says Python cannot because it must read its own
installation, which is not readable to ALL APPLICATION PACKAGES. A Rust
binary has no installation. That is an argument, not a measurement.

**The spike.** A throwaway Rust program, written before alpha.1, that:

- creates an AppContainer profile (`CreateAppContainerProfile`) with a
  capability set, and starts a copy of itself inside it
  (`STARTUPINFOEX` with `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES`);
- from inside, attempts and **reports** each of: reading its own
  executable; reading a file in a directory granted by an explicit ACE
  for the container SID; reading a file outside it; writing inside and
  outside; opening a TCP connection with and without the
  `internetClient` capability; starting a process; reading standard
  input and writing standard output, which the tool door needs;
- writes one line per attempt saying allowed or refused with the error,
  and exits.

**What it must show**: reads held to the granted directory, the network
refused without the capability, standard input and output still working,
and a granted directory reachable by adding one ACE for the container
SID at run time rather than by asking a user to relabel anything.

**Time box: 5 days.** If it does not show those things in five days, the
result is written into THREAT_MODEL.md as a measurement, alpha.4 ships
with Windows exactly as it is today, and the claim that 9.0 makes
Windows confinement strictly better is removed from 0002 and from the
release note rather than softened.

### 4. crates.io supply chain

**What it is.** A second registry, a second lockfile, and a language
whose culture is many small dependencies. sabline-lang depends on z3 and
llvmlite, both optional. sabline-rt must not arrive with two hundred
transitive crates.

**The policy**, on every leg, both of them:

- **`cargo deny check`** - advisories, licences, bans and **sources**:
  no registry but crates.io, no git dependency, no path dependency
  outside the workspace.
- **`cargo vet`** - every dependency, and every version bump, has an
  audit record in the repository. `cargo vet` is the one that makes a
  Dependabot bump a thing a person looks at rather than a thing that
  merges.
- **A cap, argued rather than assumed**: **25 direct and transitive
  crates** for the default build. A pull request that crosses it states
  in its description what the crate does, what it would take to write
  that ourselves, and why not - the same discipline as a
  `compatibility:` line. The target for the confinement work is the raw
  system calls, not a wrapper crate: the Landlock and seccomp code in
  `sabline/confine.py` is `ctypes` against the kernel ABI, and the Rust
  version should be the same against `libc`.
- `Cargo.lock` is committed, and the release builds from it.
- Actions in the Rust workflow are pinned by commit, as MAINTENANCE.md
  requires for jobs that sign or publish.

### 5. `unsafe`

**What it is.** Landlock, seccomp, `sandbox_init`, the AppContainer, and
every C ABI entry point are `unsafe` and cannot be otherwise. `unsafe`
in the confinement layer is `unsafe` in the thing whose job is to be the
box.

**The rule**, checked by CI and not by intention:

- `#![forbid(unsafe_code)]` on every module that does not need it, which
  is the whole of the lexer, parser, checkers and interpreter.
- The crate has `unsafe_op_in_unsafe_fn` denied, so an `unsafe fn` does
  not silently make its body unsafe.
- **Every `unsafe` block carries a `// SAFETY:` comment saying which
  invariant makes it sound, and a test that would fail if that invariant
  were broken.** A lint job greps every `unsafe` block for the comment
  and fails without one; a second scan requires each `// SAFETY:` to
  name a test by name, and requires that test to exist.
- `cargo miri test` on the parts Miri can run (everything but the system
  calls) on the Linux leg.
- The C ABI is fuzzed (alpha.7) for exactly the inputs an `unsafe`
  boundary gets wrong: null, non-UTF-8, use-after-free, two threads.

There is no target of "as few as possible". A count is not a property; a
reason and a test are.

### 6. The mechanized proof

**What it is.** Everything above is testing. Two implementations
agreeing over 700 programs is evidence, not proof, and this project's
own rule 1 - never claim something is proven when it is not - applies to
the project as much as to a program's promises. A mechanized proof is
the one thing that would let Goal A and Goal C be stated as theorems
about a calculus rather than as claims about a test suite.

**Lean 4** is recommended: it has the largest active community for this
kind of work, `mathlib` for the arithmetic, and a proof term that a
reader can check with a small kernel.

**Which core.** Not Sabline. A core calculus, small enough to finish:

- expressions: literals (Int, Bool, Text), variables, binary operators,
  and calls;
- statements: `let`, assignment, `if`, `while`, `return`, and one
  primitive `perform(e, r, v)` where `e` is an effect, `r` a resource
  name and `v` a value - which stands for every builtin that touches
  anything;
- function definitions with a declared effect set, and the transitive
  rule over the call graph;
- a budget `B` as a set of pairs of an effect and a decidable predicate
  over resource names, with `permits(B, e, r)`;
- a small-step semantics over configurations `⟨s, ρ, B, t⟩` where `t` is
  the trace of performed operations;
- for the second theorem only: the `Secret` fragment - a two-point
  lattice on types, the propagation rule, the sink rule, and the
  no-branch rule.

No proofs, no contracts, no generics, no records, no native code, no
termination checking, no `Untrusted`. Each of those is a place where the
proof would grow without saying anything new about the two properties.

**The two theorems.**

- **Budget non-escape (Goal C).** If `⟨s, ρ, B, []⟩ →* ⟨s', ρ', B, t⟩`
  then every `perform(e, r, v)` in `t` satisfies `permits(B, e, r)`. A
  preservation argument: the budget is never widened by any rule, and
  the only rule that appends to the trace has `permits` as a premise.
  This is the easier one and is worth doing on its own.
- **Secret non-interference (part of Goal B's neighbourhood, and 7.0's
  claim).** For two initial environments low-equivalent (equal on every
  value whose type does not carry `Secret`), the two runs produce equal
  traces restricted to `perform` operations - the observable part. The
  no-branch rule (E563) is what makes this hold and is why 7.0 exists;
  a mechanization that could not prove it without that rule would be
  evidence the rule is necessary, which is worth having either way.

**How long.** For someone who already knows Lean 4: the calculus and
budget non-escape, 6 to 10 weeks part time; non-interference, 8 to 12
more. Call it **3 to 5 months part time**. The maintainer does not know
Lean 4, so the honest options are (a) learn it, which doubles that
estimate and is the only one that does not depend on anyone else; (b)
find a collaborator, which is the best outcome and cannot be scheduled;
(c) do budget non-escape only and say so. **(c) is the plan of record**,
and (b) is the one to ask for.

**What it would and would not say.** It would say the *calculus* cannot
escape its budget. It would not say sabline-rt cannot, and it must never
be reported as saying that. The distance between the calculus and the
implementation is the conformance corpus and the agreement gate, and a
paper or a README that blurs the two would be doing the thing this
project criticises other projects for.

**It is not on the 9.0 critical path.** It does not gate any alpha and
does not gate the rc. It is here because a risk register that lists only
the risks with a mitigation is a marketing document.
